# GGOBIS (꼬비스) — LoL 라인 카운터 / 바텀 듀오 / 픽 추천 (다중 소스)

리그 오브 레전드 전적 사이트 **6곳**(op.gg, u.gg, lolalytics, Mobalytics, DeepLoL, lol.ps)의 데이터를 요청이 들어올 때마다 실시간으로 가져와 합쳐서 보여주는 웹 앱입니다. 자체 DB나 데이터 수집 파이프라인이 없습니다 — 매 조회가 곧 각 사이트에 대한 실시간 조회입니다. 주로 모바일에서 쓰는 걸 전제로 화면을 맞췄습니다(뷰포트 자동 대응, 더블탭 확대/텍스트 선택 비활성화 — 아래 "모바일 UI" 참고).

- **라인 카운터**: 챔피언 + 라인을 고르면 그 조합을 상대하기 좋은/나쁜 챔피언과 승률을 여러 사이트에서 가져와 보여줍니다.
- **바텀 듀오 시너지**: 원거리 딜러 + 서포터 조합의 실제 시너지 승률을 여러 사이트에서 가져와 보여줍니다.
- **픽 추천**: 실제 픽창처럼 **우리팀 5칸 + 상대팀 5칸, 총 10칸**짜리 입력판에서 내가 픽할 포지션을 고르고 아는 만큼만 채우면 됩니다. 결과는 세 가지를 따로 보여줍니다.
  1. **내 픽 추천**: 실제 승률은 10칸 중 **상대의 내 포지션 칸**(라인 카운터 데이터)과, 서포터를 픽할 때는 **우리팀 원거리 딜러 칸**(듀오 시너지 데이터)에서만 가져옵니다 — 이 사이트들에 다른 포지션 상대와의 실측 승률 데이터 자체가 없기 때문입니다(카운터 페이지는 항상 같은 라인끼리만 존재). 둘 다 있으면 두 지표를 평균 내 "둘 다 좋은 픽"도 따로 보여줍니다.

     **순위에는 상대팀 전체가 반영됩니다.** 승률은 여전히 내 라인 상대(±듀오 파트너) 매치업에서만 가져오지만, 순위를 매길 때는 상대팀에 채워둔 **다른 포지션 챔피언들도** 함께 봅니다 — Riot 공식 챔피언 태그(`Tank`/`Fighter`/`Assassin`.../`info.defense`)만으로 판단하는 두 가지 신호만 씁니다: 상대팀에 탱커가 없으면 암살자 후보에게, 상대팀이 전사/암살자 위주(다이브형)면 튼튼한(탱커 태그 또는 방어력 6 이상) 후보에게 가산점을 줍니다(`scoreEnemyCompFit`, `src/lib/teamComp.ts`). CC기·이니시 성향처럼 Riot이 공식 정적 데이터로 안 주는 항목은 여기에도 넣지 않았습니다. 이 가산점은 실제 승률 대비 **25%의 낮은 비중**(`PICK_REAL_WEIGHT=0.75` / `PICK_FIT_WEIGHT=0.25`)만 차지해서, 승률 격차가 뚜렷한 픽의 순서를 뒤집는 일은 없고 비슷한 후보들 사이에서만 순위를 조금 흔듭니다. 적용된 후보에는 **"상대팀 조합에 적합"** 배지가 붙습니다. 상대팀 챔피언이 아직 하나도 안 채워져 있으면 이 가산점은 모두에게 중립(0.5)이라 순위에 아무 영향이 없습니다 — 채울수록 반영되는 정보가 늘어납니다.

     **상위 5개는 실제 스킬 조합까지 봅니다.** 위 태그 기반 가산점 위에, 표본이 있는 상위 5개 후보에 한해 Data Dragon의 챔피언별 상세 데이터(`.../data/{locale}/champion/{slug}.json` — 패시브+Q/W/E/R의 이름·설명이 담긴 공식 엔드포인트)를 후보와 상대팀 전원에 대해 조회해서 실제 스킬 구성으로 한 번 더 순위를 다듬습니다(`applySkillFitBonus`, `src/lib/championSkills.ts`). 예를 들어 상대팀에 하드 CC가 하나도 없으면 기동성 스킬을 가진 후보에게, 상대팀에 탈출기(기동성/보호막/회복)가 하나도 없으면 하드 CC를 가진 후보에게 가산점을 줍니다. **주의**: Riot은 "이 스킬은 기절이다" 같은 구조화된 분류를 공식적으로 제공하지 않습니다 — 이 태그는 스킬 설명 텍스트(공식 원문)를 "기절"/"속박"/"돌진"/"보호막" 같은 한국어 게임 용어로 키워드 매칭해서 추론한 것이라, 문구가 특이한 스킬은 놓치거나 잘못 분류될 수 있는 휴리스틱입니다. 표본이 있는 상위 5개에만 적용되는 이유는 위 다른 상위-N 전용 기능(파워 커브, 빌드)과 같습니다 — 후보 전체(20~40명)마다 챔피언 하나씩 별도 요청을 보내는 게 낭비이기 때문입니다. 챔피언 풀(숙련도 티어) 기능이 켜져 있으면 이 재정렬은 절대 티어 순서를 건드리지 않고 같은 티어 안에서만 순위를 조정합니다.
  2. **실측 데이터 기반 전체 시너지**: 양 팀이 같은 라인에 서로 챔피언을 채워둔 모든 라인의 실제 매치업 승률, 그리고 우리팀 원거리 딜러+서포터가 둘 다 채워져 있으면 그 듀오의 실제 시너지 승률을 — 지금까지와 똑같이 실시간 스크래핑한 진짜 숫자로 — 우리 시점 승률로 환산해서 보여줍니다. 각 라인/듀오를 평균 낸 "종합 점수"도 함께 제공합니다.

     **라인전 세부지표**: 위 라인 매치업 각각에, lol.ps의 전용 1:1 비교 엔드포인트(`https://lol.ps/api/versus/stats.json?lane={n}&champion1={ally}&champion2={enemy}` — champSummary/graphs.json과는 완전히 별개의 API로, 사용자가 Network 탭에서 직접 찾아준 요청)에서 가져온 15분 골드/경험치/CS 차이(아군 기준, 양수면 아군 우위), 15분 이전 솔로킬 수, 최대 레벨 리드, 6레벨 우위 비율, 표본 게임 수를 함께 보여줍니다(`getVersusStats`, `src/lib/sources/lolps.ts`). 이 엔드포인트는 챔피언 하나의 페이지가 아니라 **두 챔피언을 동시에 지정**해야 하는 진짜 1:1 비교 API라서, 이미 아군/적군이 둘 다 정해진 라인에서만 자연스럽게 쓸 수 있습니다(추천 후보 목록처럼 상대가 여럿인 곳엔 안 붙였습니다 — 후보마다 별도 요청이 필요해서). 응답에 있는 KDA·데미지/분·시야점수·전체 승률 같은 필드는 라인전(15분 이전) 지표가 아니라 게임 전체 지표라서 의도적으로 안 씀. `version`/`tier`/`region` 파라미터는 graphs.json과 같은 이유로 생략(현재 값으로 기본 동작하길 기대, 미확인). 라인마다 이 `getVersusStats` 조회와 그 라인의 6개 소스 카운터 집계 조회는 서로 무관해서, 순차로 기다리는 대신 동시에 시작해두고 필요할 때 결과를 기다리는 방식으로 처리합니다(둘 다 실제로 순서를 지킬 필요가 없는데도 처음엔 순차 `await`로 짜여있던 걸 나중에 발견해서 고침).
  3. **챔피언 특성 기반 조합 분석**: 위와 달리 **승률 데이터가 전혀 없어도** 계산되는 보조 지표입니다. Riot Data Dragon이 공식으로 발표하는 챔피언 태그(전사/탱커/마법사/암살자/서포터/원거리 딜러)와 공격형/마법형 능력치(`info.attack`/`info.magic`, 0~10점)만 이용해서, 채워진 아군/적군 챔피언들의 역할군 분포·프론트라인(탱커) 유무·물리 대 마법 데미지 비중을 보여줍니다. 실제 승률 통계가 아니라 참고용 체크리스트라는 점, 그리고 CC기 보유량·이니시 성향처럼 Riot이 공식 정적 데이터로 발표하지 않는 항목은 넣지 않았다는 점을 분명히 표시해뒀습니다. (오프라인 폴백 챔피언 목록에는 `info` 값이 없어서, Data Dragon에 접속 못 하는 환경에서는 데미지 비중 없이 태그 정보만 나옵니다.) — 1번의 "상대팀 조합에 적합" 가산점(`scoreEnemyCompFit`)도 같은 태그/능력치 데이터를 쓰지만 용도가 다릅니다: 이건 **이미 채워진 두 팀 조합 자체**를 요약해서 보여주는 지표고, 1번의 가산점은 **아직 안 뽑은 내 후보 하나하나**가 상대팀과 얼마나 맞는지를 순위에 반영하는 용도입니다. `analyzeTeamComp`/`scoreEnemyCompFit` 둘 다 `src/lib/teamComp.ts`에 있습니다.

     **원거리 딜러 공격 속성 세분화**: 같은 조합 분석 카드 안에, 채워진 챔피언 중 원거리 딜러(Marksman 태그) 챔피언마다 **치명타/공속·공속·퍼센트 데미지·치명타 데미지** 네 가지 공격 속성 중 해당하는 걸 보여줍니다. 위 나머지 항목(태그 분포·프론트라인·데미지 비중)과 달리 **이건 Data Dragon 같은 공식 API에 없는 값**이라 — "이 챔피언은 치명타형이다" 같은 필드는 어디에도 없음 — 이 앱이 직접 정리해서 하드코딩한 참고용 분류표입니다(`src/lib/adcArchetype.ts`), `compConcepts.ts`의 `CONCEPT_MATCHUPS`/`CONCEPT_PILOT_TIPS`(공식 데이터 아닌 일반 LoL 지식을 정적으로 넣어둔 참고표)와 같은 종류입니다. 바텀 라인에서 흔히 보이는 핵심 챔피언 풀(23명)만 커버했고, 표에 없는 마크스맨은 조용히 빠집니다(억지로 분류하지 않음) — 최신 챔피언이나 이 표에 없는 챔피언, 그리고 패치로 실제 빌드 메타가 바뀐 경우 최신 정보와 다를 수 있다는 점을 화면에도 명시했습니다. 별도로 **"빌드 유동적"** 배지는 바루스·진처럼 매치업/메타에 따라 실제 빌드 방향(치명타/방어구 관통·고정 피해/온힛)이 자주 바뀌는 챔피언에 붙습니다 — 위 네 속성과는 독립적인 꼬리표입니다. `analyzeTeamComp`가 이 값도 함께 반환하도록 확장했습니다(`TeamCompAnalysis.adcArchetypes`).

     **탱커(탱커 서포터 포함) 생존 방식 세분화**: 같은 방식으로, 채워진 챔피언 중 탱커(Tank 태그) 챔피언마다 **보호막·방어력·데미지 감소·회복·체력** 다섯 가지 생존 방식 중 실제 킷에 해당하는 걸 보여줍니다(`src/lib/tankArchetype.ts`) — 위 원거리 딜러 속성과 완전히 같은 성격(공식 데이터 아닌 이 앱의 참고용 분류)의 하드코딩 데이터입니다. 탱커 서포터를 따로 목록에 안 넣은 이유는, Riot이 레오나·브라움·나서스·알리스타 같은 탱커형 서포터에 이미 `Tank` 태그를 함께 붙여두기 때문에 `Tank` 태그 하나로 순수 탱커와 탱커 서포터가 같이 잡히기 때문입니다. 핵심 탱커 풀(17명)만 커버했고, 킷을 봐도 이 다섯 범주 중 뚜렷하게 해당하는 게 없는 챔피언(아무무·세주아니 등)은 억지로 채우지 않고 표에서 뺐습니다. 한 챔피언이 여러 속성에 동시에 해당할 수 있습니다(예: 몬드는 체력+회복, 말파이트는 보호막+방어력). `analyzeTeamComp`가 이 값도 함께 반환합니다(`TeamCompAnalysis.tankArchetypes`).

     **브루저 딜/생존 방식 세분화**: 같은 방식으로, 채워진 챔피언 중 브루저(Fighter 태그) 챔피언마다 **흡혈·공속·탱킹** 세 가지 브루저 유형 중 실제 킷에 해당하는 걸 보여줍니다(`src/lib/bruiserArchetype.ts`) — 위 두 항목과 완전히 같은 성격의 하드코딩 참고 데이터입니다. 위 원거리 딜러/탱커와 다른 점 하나: `Fighter` 태그는 정글 암살자(케인·렝가·리 신 등)·서포터(쓰레쉬)·마법사 하이브리드(다이애나·엘리스)처럼 "브루저"라 부르기 애매한 챔피언까지 폭넓게 걸쳐 있어서, 태그 하나로 대상을 다 잡는 대신 실제로 브루저로 통하는 핵심 챔피언 풀(23명)만 표에 담았고 나머지 Fighter 태그 챔피언은 표에 없는 것과 동일하게 조용히 빠집니다. "흡혈"은 탱커 항목의 "회복"(고정/비율 체력 회복 스킬)과는 구분해서, 입힌 피해에 비례해 체력을 되찾는 흡혈/옴니뱀프 계열 킷·빌드에만 붙였습니다(예: 워윅·올라프·트런들처럼 킷 자체가 흡혈을 명시하는 챔피언). `analyzeTeamComp`가 이 값도 함께 반환합니다(`TeamCompAnalysis.bruiserArchetypes`).

     **조합 컨셉(돌진·포킹·쌍포·한타·스플릿)**: 3번 항목 바로 아래, 같은 위치에 뜨는 별도 카드입니다. 채워진 아군/적군 각각을 다섯 가지 잘 알려진 LoL 조합 컨셉으로 채점합니다(`src/lib/compConcepts.ts`).
     - **돌진/이니시**: 갭클로저나 하드 CC를 가진 전사/암살자/탱커가 여럿
     - **포킹**: 사거리 900+ 스킬(Q/W/E, 공식 `range` 수치 기준)을 가지면서 기동성은 없는 마법사/원거리 딜러가 여럿
     - **쌍포/보호**: 방어력 낮은 마법사·원거리 딜러(캐리 역)와 보호막/회복/CC를 가진 서포터(보호 역)가 **둘 다** 있어야 인정
     - **한타**: 하드 CC를 가진 탱커/서포터/마법사가 여럿 (진형을 잡고 5:5를 거는 그림)
     - **스플릿 푸시**: 방어력 5 이상인 전사가 여럿 (혼자서도 버티는 듀얼리스트)

     각 컨셉은 몇 명이 해당하는지("N/채워진 인원") 그대로 보여주고, 과반(2명 이상, 쌍포는 위 두 역할이 모두 있을 때만)이 맞으면 "지배적 컨셉"으로 표시합니다. 양 팀 다 지배적 컨셉이 있으면 **포킹 > 쌍포/보호 > 돌진 > 포킹**(잘 알려진 삼각 상성)과 한타-스플릿의 관계 등 몇 가지 정적 참고 문구도 함께 보여줍니다(`CONCEPT_MATCHUPS`) — 이건 실측 승률이 아니라 **일반적인 LoL 전략 지식**이라는 걸 화면에도 명시했습니다. 스킬 사거리/CC/기동성 신호는 `championSkills.ts`를 그대로 재사용하므로 그쪽의 키워드-매칭 한계(정확한 분류가 아니라 추론)도 똑같이 적용됩니다. 픽 추천 순위(1번)에는 반영되지 않고, 이미 채워진 조합을 설명하는 용도로만 씁니다.

     **컨셉별 플레이 팁**도 지배적 컨셉이 잡히면 카드 안에 같이 뜹니다. 우리팀 카드에는 그 컨셉을 "어떻게 플레이할지"(예: 포킹형이면 "정면 교전을 피하고 사거리 밖에서 스킬로 지속적으로 딜을 넣으세요"), 상대팀 카드에는 그 컨셉을 "어떻게 상대할지"(예: 상대가 돌진형이면 "핵심 캐리는 항상 팀원 뒤에, 플래시·보호기를 아끼세요") 팁을 2~3개씩 보여줍니다. 위 상성표와 마찬가지로 **실측 데이터나 API에서 오는 값이 아니라, 이 앱이 정리해서 고정으로 넣어둔 일반적인 LoL 공략 지식**입니다(`CONCEPT_PILOT_TIPS`/`CONCEPT_COUNTER_TIPS`, `src/app/page.tsx`) — 그래서 서버가 아니라 프론트엔드에만 있고 API 응답에는 포함되지 않습니다(컨셉 라벨처럼 정적 텍스트라 서버를 왕복할 이유가 없습니다).

     **챔피언 선택 화면의 CC(하드 크라우드 컨트롤) 표시**: 위 조합 컨셉/픽 추천 순위 보정에 이미 쓰던 `championSkills.ts`의 `hasHardCC`(Data Dragon 공식 스킬 설명 텍스트에서 "기절"/"속박"/"침묵"/"매혹"/"공포"/"도발"/"수면"/"제압"/"공중으로 띄워"/"이동 불가" 같은 키워드로 추론한 값 — 키워드 매칭 휴리스틱이지 Riot 공식 분류는 아님, 위 답변 참고)를 챔피언 선택 화면(10칸 입력판) 자체에도 노출했습니다. 슬롯에 챔피언을 넣으면 이름 옆에 작은 점이 붙어서 빨간 점=하드 CC 보유, 빈 점=CC 없음, 점선 회색 점=아직 확인 중이거나 조회 실패(Data Dragon 응답 없음 등)를 나타냅니다 — "없음"과 "모름"을 같은 표시로 뭉치지 않도록 세 가지 상태를 구분했습니다. 우리팀/상대팀 컬럼 아래에는 **CC 보유 챔피언 — 우리팀 N/채워진 인원 · 상대팀 M/채워진 인원** 합계도 함께 보여줍니다(`ccInfo`, `src/app/api/pickadvice/route.ts`). 별도 네트워크 요청은 추가되지 않았습니다 — 조합 컨셉 분석이 이미 채워진 챔피언 전원의 스킬 데이터를 Data Dragon에서 가져오고 있어서(`fetchAbilitiesMap`), 그 결과를 재사용만 한 것입니다.

  나머지 칸(예: 서로 채워지지 않은 라인)은 지금 당장은 위 세 계산 어디에도 쓰이지 않는, 더 많은 사이트를 연동하면 활용할 수 있도록 미리 마련해둔 자리라는 걸 화면에도 명시해뒀습니다. 1번 시너지 추천(정확한 페어 하나에 대한 실제 승률)이 서포터를 픽할 때만 제공되는 이유는, 확인된 사이트 데이터가 "원거리 딜러 → 시너지 좋은 서포터" 방향의 목록만 있고 반대 방향이나 탑/정글/미드의 팀 시너지 데이터는 확인된 소스가 없기 때문입니다 — 이 제약은 그대로지만, 아래 "전 포지션 시너지 교집합" 기능으로 다른 포지션에도 (더 거친 형태로) 반영했습니다.

  **전 포지션 시너지 교집합**: op.gg 등의 "시너지" 페이지가 원래 ADC 전용이 아니라 포지션 세그먼트(`/synergies/{position}`)를 받는다는 걸 활용해서, `getBotDuoCandidates`/`getBotDuoSynergy`를 ADC 전용에서 모든 포지션으로 일반화했습니다(`src/lib/sources/genericSource.ts`, `registry.ts`). 이걸로 "우리팀에 이미 채워둔 챔피언 여러 명과 각각 시너지 좋은 챔피언의 교집합"을 계산합니다: 채워진 아군 한 명 한 명에 대해 그 챔피언 자신의 포지션 기준 시너지 파트너 상위 20명을 실제 스크래핑 데이터로 가져온 뒤(`computeAllySynergyScores`), 후보 챔피언이 몇 명의 아군과 겹치는지(`matchCount`/`outOf`)와 겹친 아군들에 대한 평균 실제 승률을 계산합니다 — **전원과 겹치면(matchCount === outOf) 진짜 교집합**이고, 일부만 겹쳐도 몇 명과 겹치는지 그대로 보여줍니다(빈 결과를 조용히 숨기지 않음). "라인전 유리한 픽"/"시너지 좋은 픽" 두 목록 모두에 **우리팀 N명 중 M명과 시너지 좋음 (평균 X%)** 배지로 표시되고, 순위에도 반영됩니다: 기존에는 실제 라인전 승률 75% + 상대 조합 태그 휴리스틱 25%였던 가중치를, 실제 라인전 승률 65% + 상대 조합 태그 휴리스틱 15% + **이 실측 아군 시너지 데이터 20%**로 재분배했습니다(`PICK_REAL_WEIGHT`/`PICK_ENEMY_FIT_WEIGHT`/`PICK_ALLY_SYNERGY_WEIGHT`, `rerankPicks`) — 태그 휴리스틱보다 실측 데이터에 더 높은 비중을 주되, 여전히 직접적인 라인전 승률이 압도적 1순위입니다. **알려진 한계**: 5명 전체가 함께 나온 매치 데이터가 아니라 "챔피언 하나당 시너지 파트너"를 아군별로 독립적으로 조회해서 겹치는 걸 찾는 방식이라, 진짜 5:5 조합 승률과는 다릅니다(원본 매치 데이터 없이는 계산 불가능 — README 앞부분 "실제 매치 기록" 관련 논의 참고). 상위 20명 안에 들지 않으면 매치로 안 잡히므로, 표본이 적은 조합은 실제로 시너지가 있어도 놓칠 수 있습니다.

  **파워 커브(초반/후반 성향)**: 1번 "내 픽 추천" 목록의 상위 5개 후보에는 lol.ps의 분당 승률 그래프(`/api/champ/{id}/graphs.json`)를 추가로 붙여서 "초반 몇 %, 후반 몇 %"를 함께 보여줍니다. 둘의 차이가 크면 "(초반형)"/"(후반형)" 표시도 붙습니다. 이 데이터는 op.gg 등의 카운터/승률 데이터와는 별개로, lol.ps만 제공하는 값입니다. 사용자가 브라우저에서 HAR(전체 네트워크 캡처)을 떠서 찾아준 덕분에 발견한 엔드포인트라, `version`/`tier`/`region` 파라미터는 op.gg의 `patch`와 같은 이유로 일부러 뺐습니다(생략 시 최신 데이터로 기본 동작하길 기대하는 것으로, 아직 확정은 아님) — 그리고 champSummary와 같은 한계로 이 값도 그 챔피언 자신의 주 라인 데이터만 주기 때문에, 요청한 포지션과 일치할 때만 붙습니다. 표본이 많은 상위 5개에만 붙는 이유는 후보 목록 전체(20~40명)에 대해 매번 추가로 그래프를 조회하는 게 낭비이기 때문입니다.

  **파워 커브·라인전 세부지표를 순위에도 반영**: 위 두 신호(팀 파워 커브, 라인전 세부지표)는 처음엔 표시 전용이었는데, 이제 상위 5개 후보의 순위 자체에도 반영됩니다(`refineTopWithPowerCurveAndLaning`, `src/app/api/pickadvice/route.ts`, `refineTopWithSkillFit` 다음 단계로 실행돼서 최종 순위를 정함). 새 최상위 가중치를 따로 추가하는 대신(그러면 `PICK_REAL_WEIGHT`/`PICK_ENEMY_FIT_WEIGHT`/`PICK_ALLY_SYNERGY_WEIGHT`를 또 재분배해야 함), 두 신호를 개념적으로 가장 가까운 기존 가중치 슬롯에 **블렌딩**해 넣는 방식을 택했습니다:
  - **팀 파워 커브 적합도**: 이미 채워진 아군 라인들의 팀 파워 커브가 가장 강한 구간(초반/중반/후반, `teamPeakPhase`)에 후보 자신의 그 구간 승률이 얼마나 부합하는지를 0.5~1.0 스케일로 변환(`phaseFitScore`)해서, `allySynergyFit`에 **30%**(`POWER_CURVE_TEAM_FIT_BLEND`) 비중으로 섞습니다 — "우리팀 계획에 맞는 픽"이라는 성격이 아군 시너지 적합도와 같은 결이라 그 슬롯에 넣었습니다.
  - **라인전 세부지표 적합도**: "라인전 카운터" 추천(내 라인 상대가 정해져 있는 경우)에 한해, 후보와 그 상대의 실제 15분 골드 차이(`versus/stats.json`)를 0.5~1.0 스케일로 변환(`laningFitScore`, ±2000골드를 대략 한 등급 스윙으로 간주 — 별도 근거 데이터가 없어 보수적으로 잡은 값)해서, 실제 승률(`goodness`) 항목에 **25%**(`LANING_STATS_BLEND`) 비중으로 섞습니다 — 이건 실측 매치업 데이터라 태그 기반 적합도가 아니라 실제 승률 쪽에 더 가깝다고 판단했습니다. "시너지 좋은 픽"(바텀 듀오 시너지)은 특정 상대 라이너가 없어서 이 절반은 건너뜁니다.

  최상위 가중치(`PICK_REAL_WEIGHT=0.65`/`PICK_ENEMY_FIT_WEIGHT=0.15`/`PICK_ALLY_SYNERGY_WEIGHT=0.2`)는 그대로 유지되고, 두 신호는 그 안에서만 순위를 조금 더 흔듭니다. `combinedPicks`("둘 다 좋은 픽")는 이번엔 건드리지 않았습니다 — counterPicks/synergyPicks가 이미 반영된 뒤의 `winRate`/`compFit`/`allySynergyFit`을 그대로 평균만 내는 구조라 새 신호도 간접적으로는 섞여 들어가지만, 별도 블렌딩 로직을 추가하진 않았습니다.

  **버그 수정 — 파워 커브도 라인 불일치 캐비어트가 빠져있었음**: 위 도입 당시, `getPowerCurve()`가 반환하는 `actualPosition`(이 수치가 실제로 어느 라인 기준인지)을 한 번도 확인하지 않고 `earlyWinRate`/`lateWinRate`를 그대로 붙이고 있었습니다 — `annotateWithBuild`/`computeTeamPowerCurve`는 이미 라인이 다르면 `laneNote`로 표시하는데, 이 함수만 빠뜨린 채였습니다. 예를 들어 원딜 추천에서 상위 후보의 lol.ps 주 라인이 정글이면, 그 정글 데이터를 아무 경고 없이 "초반/후반 승률"로 보여주고 있었던 것 — 바로 아래 빌드 카드는 정상적으로 "⚠ 정글 라인 데이터만..." 경고를 붙이는데도 파워 커브 배지만 조용했습니다. `powerCurveLaneNote` 필드를 추가해서 같은 방식으로 고쳤습니다.
- **빌드 추천** (룬/스펠/아이템/스킬 순서): lol.ps 챔피언 페이지에 이미 내장돼 있던 같은 `champSummary` 블록에서 카운터 데이터와 함께 뽑아냅니다 — 별도 네트워크 요청이 추가로 필요 없습니다. 세 곳에서 볼 수 있습니다.
  1. **빌드 탭**: 챔피언+라인만 고르면 룬(메인/서브 트리+개별 룬), 스펠 조합, 시작 아이템, 핵심 3아이템, 전체 빌드 순서(신발 포함), 스킬 마스터리 순서, 레벨 1~15 스킬업 순서를 각각의 승률/표본 수와 함께 보여줍니다.
  2. **라인 카운터 결과**: 조회한 기준 챔피언의 빌드 카드가 카운터 목록 아래에 자동으로 같이 붙습니다.
  3. **픽 추천 결과**: "내 픽 추천"/"시너지 좋은 픽" 상위 5개 후보 각각에, 룬 키스톤+스펠+핵심 아이템만 담은 축약 카드가 **lol.ps·DeepLoL 두 소스 모두** 따로따로 붙습니다(각각 "lol.ps"/"DeepLoL" 라벨로 구분 — 두 소스를 합산하지 않는다는 원칙은 그대로). 원래는 lol.ps 하나만 붙어있었는데, 라인 카운터 결과/빌드 탭엔 이미 있던 DeepLoL 빌드가 여기만 빠져 있어서 똑같이 추가했습니다(`annotateWithDeeplolBuild`, `src/app/api/pickadvice/route.ts`) — DeepLoL은 lol.ps와 달리 라인이 진짜로 구분돼 있어서(주 라인 한정 아님) 라인 불일치 처리가 아예 필요 없습니다. lol.ps 빌드 조회(`annotateWithBuild`)와 DeepLoL 빌드 조회(`annotateWithDeeplolBuild`)는 서로 다른 필드(`build`/`buildDeeplol`)에만 쓰기 때문에 순차 `await` 대신 `Promise.all`로 동시에 실행합니다(처음엔 순차 실행이라 두 조회 시간을 그대로 더해서 기다리고 있었음 — 나중에 발견해서 고침).

  **빌드 데이터를 순위에도 반영**: 두 소스에서 가져온 후보의 실제 추천 핵심 아이템에 상대팀 데미지 타입(물리/마법)에 맞는 방어 아이템이 포함돼 있으면 순위에 소폭 가산점을 줍니다(`applyBuildFitBonus`, 같은 파일). Data Dragon `item.json`이 아이템마다 공식으로 붙여주는 `tags`(예: `"Armor"`, `"SpellBlock"`)를 그대로 씀 — 이 값을 이 앱에서 처음 파싱해서 `DDragonItem.tags`로 노출함(`src/lib/ddragon.ts`). 상대팀의 물리/마법 데미지 비중이 60% 이상으로 확실히 한쪽에 치우쳐 있을 때만(`DAMAGE_MAJORITY_THRESHOLD`) 판단하고, lol.ps·DeepLoL 둘 중 하나라도 그 방향 아이템(방어력 태그면 물리, 마법 저항력 태그면 마법)을 핵심 아이템에 포함하면 `compFit`에 +0.15(`BUILD_DEFENSE_BONUS`)를 더합니다 — `scoreEnemyCompFit`/`applySkillFitBonus`(둘 다 `src/lib/teamComp.ts`)와 같은 "공식 정적 데이터만, 작은 가산점, 1로 클램프" 방식을 그대로 따른 것입니다. 이 가산점도 결국 `compFit`을 통해 기존 `PICK_ENEMY_FIT_WEIGHT`(15%) 비중 안에서만 순위에 영향을 주므로, 실제 승률의 압도적 우위는 여전히 그대로입니다. 이 재정렬(그리고 팀 파워 커브·라인전 세부지표 재정렬)이 서로 다른 곳에서 각자 순위 공식을 따로 베껴 쓰고 있던 걸 발견해서, 공통 `pickRankScore()` 함수 하나로 합쳤습니다 — 나중에 신호를 하나 더 추가할 때 한쪽 재정렬 단계에서만 반영되고 다른 단계에서 사라지는 버그를 막기 위함입니다.

  아이템/스펠/룬 이름·아이콘은 Riot Data Dragon의 공식 정적 데이터(`item.json`/`summoner.json`/`runesReforged.json`)로 채웁니다. 룬 아이콘 경로만 다른 Data Dragon 이미지들과 달리 패치 버전이 안 붙는 `/cdn/img/` 접두사를 쓴다는 걸 확인해서 별도 처리했습니다. champSummary 데이터를 재사용하다 보니 파워 커브/카운터와 완전히 같은 한계를 그대로 물려받습니다: 그 챔피언의 **주 라인 데이터만** 제공되므로 요청한 포지션과 다르면 에러로 표시되고(`getChampionBuild`), 파워 커브와 마찬가지로 픽 추천에서는 표본이 있는 상위 5개 후보에만 조회를 붙입니다. 이 버전 없는 룬 아이콘 경로가 배포 환경에서 `net::ERR_INVALID_RESPONSE`로 깨지는 사례가 실제로 보고돼서, 모든 Data Dragon `<img>`에 `referrerPolicy="no-referrer"`를 붙여뒀습니다(`ChampionIcon.tsx`/`BuildCard.tsx`) — 리퍼러 기반으로 요청을 이상하게 처리하는 CDN 엣지가 원인일 가능성이 있어서 넣은 방어적 조치이며, 이 저장소 환경 자체가 아웃바운드 네트워크가 막혀 있어 직접 재현/검증은 못 했습니다.
- **챔피언을 넣을 때마다 자동으로 다시 조회**: 픽 추천은 처음엔 "픽 추천 받기" 버튼을 눌러야만 조회됐는데, 이제 슬롯에 챔피언을 넣거나 뺄 때마다(포지션 탭을 바꾸거나 챔피언 풀을 바꿀 때도) 자동으로 다시 조회됩니다. 슬롯 하나라도 채워지면 조회 조건이 충족되는(`canRun`) 걸 그대로 재사용해서, 그 상태가 바뀔 때마다 500ms 디바운스 후 `runLookup()`을 실행합니다(`useEffect`, `src/app/page.tsx`) — 여러 슬롯을 빠르게 연달아 클릭해도 마지막 변경 후 500ms간 조용해야 그때 한 번만 조회해서, 클릭할 때마다 6개 사이트를 매번 스크래핑하는 낭비를 막습니다. 느린 응답이 그 사이 시작된 더 최신 요청을 덮어쓰지 않도록 요청마다 증가하는 ID로 최신 여부를 확인하고, 오래된 응답은 도착해도 조용히 버립니다(`requestIdRef`). 버튼은 "지금 바로 새로고침"으로 남겨뒀습니다 — 디바운스를 기다리지 않고 바로 조회하고 싶을 때 씁니다. 라인 카운터/듀오 시너지/빌드 세 탭은 그대로 버튼을 눌러야 조회됩니다(단일/두 슬롯짜리라 자동 조회의 이점이 적다고 판단).

  **버그 수정 — 라인 카운터/빌드 탭의 배경 빌드 조회에는 이 최신 여부 확인이 빠져있었음**: "라인 카운터" 탭의 DeepLoL·lol.ps 빌드 카드, "빌드" 탭의 DeepLoL 카드는 메인 조회가 끝난 뒤 별도로(백그라운드에서) 한 번 더 요청을 보내는 구조인데, 이 두 번째 요청의 응답 처리(`setCounterBuild`/`setBuildResultDeeplol`)에는 `isStale()` 확인이 빠져 있었습니다 — 챔피언 A를 조회한 직후(그 배경 요청이 아직 안 끝난 상태에서) 챔피언 B로 바꿔 다시 조회하면, 나중에 도착한 A의 빌드 카드가 화면엔 B의 카운터 목록 아래 잘못 붙는 경우가 있었습니다. 다른 모든 요청과 똑같이 `isStale()` 확인을 추가해서 고쳤습니다.
- **실제 챔피언 선택 화면 스타일 UI**: 픽 추천 탭의 10칸 입력판을 실제 LoL 챔피언 선택 화면과 비슷한 구조로 바꿨습니다 — 위쪽에 큰 스플래시 아트 미리보기, 그 아래 우리팀(파란 테두리)/상대팀(빨간 테두리) 두 개의 세로 열(각 5칸, 탑→정글→미드→원딜→서폿 고정 순서)로 나눠서 보여줍니다(`.champ-select`, `src/app/page.tsx`). 챔피언을 하나 고를 때마다 그 챔피언의 스플래시 아트(`https://ddragon.leagueoflegends.com/cdn/img/champion/splash/{slug}_0.jpg` — 룬 아이콘과 같은 패치 버전 없는 경로)가 미리보기 영역에 크게 뜹니다. 모바일 화면 폭을 고려해서 실제 클라이언트처럼 좌우 넓은 레이아웃 대신 좁은 두 열로 압축했고, 역할 아이콘 이미지 대신(Data Dragon이 역할 아이콘을 별도로 제공하지 않음) 짧은 텍스트 라벨("탑"/"정글"/...)을 씁니다.
- **팀 파워 커브 (초반/중반/후반)**: 픽 추천 화면에서 우리팀 라인에 채워둔 챔피언들의 lol.ps 분당 승률 그래프를 종합해서, **팀 전체가 어느 구간(초반/중반/후반)에 가장 강한지**와 **각 라이너가 초반형/후반형/균형형 중 어디에 가까운지**를 따로 보여줍니다(`teamPowerCurve`, `computeTeamPowerCurve`, `src/app/api/pickadvice/route.ts`). 각 라이너의 수치는 lol.ps `graphs.json`을 3등분(초반/중반/후반)해서 평균 낸 실제 값이고, 팀 수치는 데이터가 있는 라이너들만 평균 낸 값입니다(빈 라인은 평균에서 제외, 0으로 채우지 않음). "초반형/후반형" 판정은 픽 추천 후보 카드에 이미 쓰던 것과 **같은 ±3%p 기준**(`PowerCurveBadge`)을 재사용합니다. lol.ps는 챔피언의 주 라인 데이터만 주기 때문에, 그 라인이 실제 배정된 포지션과 다르면 **무조건 그대로 보여주면서** 라이너 카드에 안내 문구를 붙입니다(`laneNote`) — 처음엔 빌드 탭과 같은 "그 포지션이 게임의 7% 이상일 때만"(`getLaneShare`) 규칙을 썼는데, `getLaneShare`가 의존하는 `top1LaneId`/`top1LaneRatio` 필드명 자체가 검증된 적 없는 값이라 실제로는 항상 0을 반환해서 **라인이 하나라도 안 맞으면(흔한 경우) 팀 전체가 "데이터를 찾지 못했다"고 뜨는 버그**가 있었습니다 — 배포 후 실제로 이 증상이 보고돼서(`sampledCount`가 항상 0), 이 섹션에서는 그 게이트를 완전히 빼고 항상 보여주는 쪽으로 바꿨습니다. `annotateWithBuild`(픽 추천 후보 카드의 빌드)도 같은 `getLaneShare` 게이트를 쓰고 있어서 같은 버그(오프-라인 후보의 빌드 카드가 예상보다 적게 뜸)가 있었는데, 이제 이 섹션·`/api/build`("빌드" 탭)와 똑같은 방식으로 고쳤습니다 — 게이트를 완전히 빼고, 라인이 다르면 `laneNote`로 표시만 하면서 항상 보여줍니다. `LANE_MISMATCH_MIN_SHARE` 상수와 `getLaneShare` import는 더 이상 이 라우트에서 쓰지 않아 제거했습니다(`getLaneShare` 함수 자체는 `lolps.ts`에 그대로 남아있지만, 이제 이 앱 어디에서도 호출하지 않습니다 — 검증되지 않은 필드명에 의존하는 게이트라 애초에 신뢰하기 어려웠습니다).
- **내 챔피언 풀(숙련도 우선순위)**: 픽 추천 화면 상단의 "내 챔피언 풀" 패널에서 자신이 실제로 플레이하는 챔피언을 **1티어(가장 숙련)/2티어/3티어**로 등록해두면, "내 픽 추천"(1번 항목)의 카운터·시너지·둘 다 좋은 픽 세 목록 전부가 **그 풀 안에서만** 추천되고, 승률 순위보다 **티어 순서가 먼저** 적용됩니다(같은 티어 안에서만 지금까지의 승률 순위로 정렬). 한 챔피언은 한 번에 한 티어에만 속하며, 다른 티어로 다시 등록하면 이전 티어에서는 자동으로 빠집니다. 아무 챔피언도 등록하지 않으면 지금까지처럼 전체 챔피언을 대상으로 추천합니다(기본값). 이 풀은 서버에 저장되지 않고(자체 DB가 없으므로) 브라우저 `localStorage`에만 저장되어 새로고침/재방문에도 유지되지만 기기·브라우저 간에는 공유되지 않습니다. `/api/pickadvice`에 `tier1`/`tier2`/`tier3` 쿼리 파라미터(챔피언 ID 콤마 목록)로 전달되며, 필터링은 클라이언트가 아니라 서버에서 이뤄집니다 — 그래서 파워 커브/빌드 조회(위 두 항목)도 풀 필터링 **이후의** 상위 5개에만 걸려서, 등록 안 한 챔피언 페이지를 불필요하게 조회하지 않습니다.
- 매칭당 표본(게임 수)이 가장 많은 소스를 대표값으로 쓰고, **표본이 많은 순으로 최대 3개 소스**를 함께 보여줍니다.

## 기술 스택

- Next.js (App Router, TypeScript) — 프론트엔드 + API 라우트
- Data Dragon — 챔피언 이름/아이콘 등 정적 데이터 (공식, 무료, 인증 불필요)
- 6개 사이트 실시간 스크래핑 — `src/lib/sources/`

DB도, API 키도 필요 없습니다. `npm install && npm run dev`만으로 뜹니다.

## 동작 원리

1. 챔피언 목록/아이콘은 Data Dragon에서 가져옵니다 (`src/lib/ddragon.ts`, 1시간 캐시, 오프라인이면 `data/fallback-champions.json`으로 대체 — 이 파일은 `fs.readFile(path.join(process.cwd(), ...))`가 아니라 정적 `import`로 불러옵니다. 런타임에 조립한 파일 경로는 Next.js가 추적을 못 해서 Vercel 서버리스 번들에 안 딸려갈 수 있는 잘 알려진 함정이라, 로컬(`next dev`)에서는 멀쩡히 동작하다가 배포 후에만 깨질 수 있습니다).
2. 카운터/듀오를 조회하면 등록된 6개 소스에 **동시에** 요청을 보냅니다 (`src/lib/sources/aggregate.ts`, `Promise.allSettled`로 일부가 실패해도 나머지로 계속 진행).
3. 각 소스는 해당 챔피언의 페이지를 fetch해서, 페이지에 내장된 상태를 파싱해 통계를 뽑아냅니다 (`src/lib/scrape.ts`). 두 가지 임베딩 방식을 지원합니다: 구형 `__NEXT_DATA__`/`__NUXT__` 단일 JSON 블록, 그리고 최신 Next.js App Router가 쓰는 `self.__next_f.push(...)` RSC Flight 스트림(여러 개의 `id:value` 줄로 쪼개져 있고, 값 부분만 따로 JSON 파싱). op.gg가 실제로 후자 방식이라는 걸 실제 페이지 소스로 확인했습니다.
4. 같은 상대 챔피언에 대해 여러 소스가 값을 준 경우, **게임 수가 가장 많은 소스**를 대표값으로 쓰고 상위 3개 소스를 같이 보여줍니다.
5. 같은 조합을 반복 조회할 때 각 사이트에 부담을 덜 주기 위해 소스별로 10분짜리 인메모리 캐시를 씁니다 (서버 재시작/재배포 시 초기화됨 — 영구 저장소가 아닙니다).

`extractNumberField` 파서의 버그도 하나 발견해 고쳤음: `championId`/`laneId`류 필드는 순수 숫자로 박혀있지만 `runeTotalWinrate`/`startingWinrate`/`top1ThreeCoreWinrate`/`skillMasterWinrate` 같은 **승률 필드는 `"52.72"`처럼 따옴표로 감싼 문자열**이라 기존 정규식(순수 숫자만 매치)이 이 필드들만 조용히 `null`로 반환하고 있었음 — 정규식에 선택적 따옴표(`"?`)를 추가해서 두 형태를 모두 매치하도록 수정, 실제 저장해둔 나서스(챔피언ID 75) 페이지 HTML로 수정 전/후 값을 직접 대조해서 확인함(카운터 쪽 필드는 이미 순수 숫자라 회귀 없음도 같은 방식으로 확인) |

**로컬에서 실행해보고 안 되면** 에러 메시지를 그대로 알려주세요. API 응답에는 소스별로 어떤 이유로 실패했는지(HTTP 상태 코드 / 못 찾은 부분)가 다 담겨 있어서 바로 원인을 좁힐 수 있습니다. 일부만 실패하는 경우 화면의 "N개 소스 중 M개 성공" 항목을 펼치면 소스별 에러가 보입니다. 카운터 페이지 하나의 실제 URL과 (가능하면) 그 페이지 소스를 공유해주시면 가장 빠르게 고칠 수 있습니다.

**화면에는 에러 메시지를 띄우지 않습니다.** 처음에는 6개 소스가 전부 실패하면 원인 파악을 위해 URL/HTTP 상태 코드가 그대로 담긴 빨간 배너를 화면에 띄웠는데, 실사용 단계에서는 그게 사용자에게 그냥 깨진 화면처럼 보인다는 피드백을 받아서 걷어냈습니다. 지금은 어떤 조회든 전부 실패하면(예: `/api/counters`가 502를 반환) 그 결과 영역이 그냥 비어있는 채로 남고(헤더까지 포함해서 아예 안 뜸), 원본 에러는 `console.error`로만 남습니다 — 위 문단처럼 에러 메시지가 필요하면 브라우저 개발자 도구 Console 탭을 확인해주세요. 픽 추천의 "실측 데이터 기반 전체 시너지"처럼 이미 채워진 항목 옆에 표시되는 매치업 실패도 원본 에러 대신 항상 "이 매치업 데이터를 찾지 못했습니다" 같은 고정 문구만 보여줍니다. 반면 **일부만 실패하는 경우의 "N개 소스 중 M개 성공" 펼침 목록은 그대로 유지**됩니다 — 이건 알람이 아니라 접어둔 상세 정보라 화면을 어지럽히지 않으면서도 디버깅에 필요하면 펼쳐볼 수 있기 때문입니다.

## 모바일 UI

이 앱은 브라우저 탭이 아니라 **모바일 홈 화면에 앱처럼 추가해서 쓰는 걸** 기준으로 UI를 맞췄습니다.

- **뷰포트 자동 대응**: `layout.tsx`의 `viewport` export에 `width: "device-width"`, `initialScale: 1`, `maximumScale: 1`, `userScalable: false`, `viewportFit: "cover"`를 설정해뒀습니다. 어떤 화면 비율의 기기에서 열어도 그 폭에 맞춰 렌더링되고(줌 없이), 노치/펀치홀이 있는 기기에서도 `env(safe-area-inset-*)`로 상하좌우 안전 영역만큼 `.page` 패딩을 더 줍니다.
- **더블탭 확대 · 텍스트 선택 비활성화**: `body`에 `touch-action: manipulation`(더블탭 확대 제스처 자체를 브라우저가 인식하지 않게 함) + `user-select: none` / `-webkit-touch-callout: none`(길게 눌러도 선택 팝업이나 텍스트 선택이 뜨지 않음)을 적용해 네이티브 앱에 가까운 느낌으로 만들었습니다. 단, 검색창 등 `input`/`textarea`는 예외로 `user-select: text`를 다시 켜뒀습니다 — 입력한 값은 정상적으로 선택/복사할 수 있어야 하기 때문입니다.
- **상단 탭 고정(sticky) + 가로 스크롤**: 모드 탭(라인 카운터/바텀 듀오/픽 추천/빌드)과 포지션 탭은 좁은 화면에서 줄바꿈되어 지저분해지는 대신 한 줄로 유지하고 가로로 스크롤하도록 바꿨고, 모드 탭은 스크롤해도 화면 위에 붙어있습니다(`position: sticky`).
  - 이 과정에서 CSS 함정을 하나 발견해서 고쳤습니다: `html`/`body`에 가로 스크롤 방지용으로 `overflow-x: hidden`을 걸어두면, `overflow-y`가 명시돼 있지 않을 때 브라우저가 자동으로 `overflow-y: auto`로 승격시키는 스펙 규칙 때문에 `html`과 `body`가 각각 독립된 스크롤 컨테이너가 되어버립니다. 그러면 `position: sticky` 요소가 자신이 붙어야 할 스크롤 컨테이너를 잘못 찾게 되어 고정되지 않고 그냥 스크롤을 따라 지나가 버립니다. `overflow-x: hidden` 대신 `overflow-x: clip`으로 바꿔서 이 부작용 없이 가로 스크롤만 막도록 고쳤습니다(Playwright로 `getBoundingClientRect()`를 직접 찍어서 고치기 전/후 차이를 확인했습니다).
- **PWA 홈 화면 메타**: `layout.tsx`의 `appleWebApp`(`capable`, `title: "GGOBIS"`, `statusBarStyle`)로 iOS에서 홈 화면에 추가했을 때 브라우저 주소창 없이 앱처럼 열리고 이름이 "GGOBIS"로 나오게 해뒀습니다.
- **사이트 아이콘**: 기본 Next.js `favicon.ico`(레거시 폴백으로 그대로 둠) 대신, App Router의 `icon.tsx`/`apple-icon.tsx` 컨벤션(`next/og`의 `ImageResponse`로 빌드 시 렌더링)으로 브라우저 탭 아이콘(32×32)과 iOS 홈 화면 아이콘(180×180)을 직접 생성했습니다 — 배경은 `globals.css`의 `--background`(`#0b0d11`), 글자는 `--accent`(`#5b9bff`)로 앱 배색과 맞췄고, 위에 큰 글자로 "GG" + 아래에 작은 글자로 "obis"를 2줄로 넣어서 "GGOBIS"라는 사이트 이름이 읽히게 했습니다. 애플 아이콘 쪽은 iOS가 자체적으로 모서리를 둥글게 마스킹하므로 여기서는 둥근 모서리를 넣지 않고 꽉 채운 정사각형으로 만들었습니다.
- **슬롯을 누르면 챔피언 픽커로 자동 스크롤**: 챔피언 검색창+그리드(`ChampionPicker`)는 항상 페이지 맨 아래(전체 결과 섹션보다도 아래)에 렌더링되는데, 모바일에서 위쪽의 슬롯(라인 카운터/듀오/빌드의 기준 챔피언 칸, 픽 추천의 10칸 챔피언 선택 화면)을 눌러도 화면엔 아무 변화가 없어 보이는 문제가 있었습니다 — 실제로는 활성 슬롯이 바뀌어 있지만, 픽커 자체가 화면 밖 한참 아래(뷰포트 밖 1,000px 이상)에 있어서 사용자가 매번 손으로 스크롤해서 찾아야 했습니다. 슬롯을 실제로 누르는 액션(빈 슬롯 선택, 채워진 슬롯을 눌러 비우고 재선택)에서만 픽커를 부드럽게 스크롤해 화면에 띄우도록 `activateSlot`(`src/app/page.tsx`)을 추가했습니다 — 다음 빈 슬롯으로 자동 이동하거나(픽 하나 고르고 나면 스크롤 위치는 그대로 유지, 챔피언 하나씩 연달아 고를 때 매번 다시 스크롤할 필요 없음) 모드 탭을 바꿀 때는 일부러 스크롤하지 않습니다(사용자가 방금 위쪽 탭을 눌렀는데 갑자기 화면이 아래로 튀는 게 더 어색하다고 판단).
- **가시성(색 대비) 강화**: 초기 배색은 배경/카드/테두리 색이 서로 너무 가까워서(`--background`/`--surface`/`--border`가 다 비슷한 톤의 어두운 회색) 카드 경계나 비활성 탭이 잘 안 보였습니다. `--border`를 눈에 띄게 밝혀 카드/탭/아이콘 테두리가 실제로 구분되게 하고, 비활성 탭도 `--surface-alt` 배경 + `--foreground` 글자색으로 바꿔 활성 탭만 도드라지던 것에서 모든 탭이 스캔 가능하게 했습니다. 결과 카드(`.results`)에는 옅은 그림자를 줘서 배경과 확실히 분리되게 했고, `<h3>` 섹션 제목은 회색(`--muted`)이 아니라 굵은 글자 + 파란 왼쪽 테두리로 바꿔 "이게 새 섹션이다"가 한눈에 보이게 했습니다. 승률 바 트랙, 챔피언 아이콘, 티어 배지, 소스 배지도 테두리/글자 굵기/배경 불투명도를 올려서 작은 글씨들이 흐릿하게 뭉개져 보이던 문제를 줄였습니다.

## 새 사이트 추가하는 법

`src/lib/sources/registry.ts`의 `configs` 배열에 항목을 하나 추가하면 됩니다:

```ts
{
  id: "newsite",
  label: "새사이트",
  confidence: "low",
  slug: (s) => s.toLowerCase(), // 또는 toKebabSlug 등
  counterUrl: (slug, position) => `https://example.com/champions/${slug}/counters?position=${position}`,
  duoUrl: (adcSlug) => `https://example.com/champions/${adcSlug}/duos?position=adc`,
},
```

그 사이트가 Next.js/Nuxt 계열로 서버 렌더링되며 페이지에 통계 배열이 JSON으로 내장돼 있다면 이걸로 끝입니다. 완전히 다른 방식(별도 JSON API 등)을 쓰는 사이트라면 `src/lib/sources/types.ts`의 `StatSource` 인터페이스를 직접 구현하는 새 파일을 만들고 `registry.ts`의 `SOURCES` 배열에 추가하세요.

## 알려진 제한사항

- **소스별 페이지 구조 미검증** (위 "각 소스 연동 신뢰도" 표 참고) — 가장 먼저 확인이 필요한 부분입니다.
- 인메모리 캐시는 서버리스/재배포 환경에서 인스턴스마다 따로 놀고 쉽게 초기화됩니다. 완전히 신뢰할 캐시가 필요하면 Redis 등 외부 캐시로 바꾸는 걸 권장합니다.
- 어떤 사이트가 요청을 차단(403/429)하면 그대로 에러로 보여줍니다 — 우회를 시도하지 않습니다. 반복적으로 막힌다면 조회 빈도를 줄이거나 해당 사이트에 이용 허가를 문의하는 걸 권장합니다.
- 5개 챔피언 전체 조합 평가처럼 이 사이트들의 카운터/듀오/빌드 페이지에 없는 통계는 제공하지 않습니다 (실제 존재하는 데이터만 보여주는 쪽으로 방향을 잡았습니다).
- 빌드 추천은 lol.ps 한 곳의 값만 보여줍니다(다른 5개 소스와 평균/합산하지 않음) — 화면에도 "lol.ps 기준"이라고 명시해뒀습니다. 카운터/듀오처럼 여러 소스를 비교해서 보여주는 형태가 아닙니다.
- 바텀 듀오 시너지는 op.gg 등에서만 지원되고 lol.ps는 아직 미지원입니다 — lol.ps에 `duo-list.json`이라는 별도 API가 있는 걸 URL로는 확인했지만 응답 본문(Brotli 압축)을 아직 못 받아서 필드 구조를 모릅니다.
- 내 챔피언 풀은 브라우저 `localStorage`에만 저장됩니다 — 계정/서버 개념이 없어서 다른 기기나 브라우저에서는 다시 등록해야 합니다. 또한 픽 추천의 "내 픽 추천"(카운터/시너지/둘 다 좋은 픽) 세 목록에만 적용되고, 실측 데이터 기반 전체 시너지·챔피언 특성 기반 조합 분석·라인 카운터/빌드 탭에는 적용되지 않습니다(그 기능들은 "무엇을 픽할지 추천"이 아니라 이미 정해진 챔피언을 분석/조회하는 기능이라 풀 필터링 대상이 아닙니다).
- 모바일 UI를 위해 페이지 전체에서 텍스트 선택을 꺼뒀습니다(검색창 등 입력 필드는 예외). 그래서 위 "로컬에서 실행해보고 안 되면" 항목에서 안내하는 것처럼 에러 메시지를 드래그로 복사하기는 어렵습니다 — 브라우저 개발자 도구(Console/Network 탭)에서 복사하거나 스크린샷으로 공유해주세요.
- "상대팀 조합에 적합" 스킬 가산점(`championSkills.ts`)의 CC/기동성/보호막·회복 태그는 Riot이 공식으로 분류해서 주는 값이 아니라, 스킬 설명 원문을 한국어 키워드로 매칭해서 이 앱이 추론한 값입니다. 문구가 특이하거나 새로 추가된 챔피언의 스킬은 잘못 분류되거나 아예 태그가 안 붙을 수 있습니다 — 승률 대비 비중을 낮게(25%) 잡아둔 것도 이 때문입니다. 정확한 태그가 필요하면 `src/lib/championSkills.ts`의 `HARD_CC_TERMS` 등 키워드 목록을 직접 보정해주세요.
- 조합 컨셉(돌진/포킹/쌍포/한타/스플릿)과 그 상성표(`compConcepts.ts`)는 실측 데이터가 전혀 아닙니다 — 감지는 위 스킬 키워드 휴리스틱 위에 얹은 또 다른 근사치고, 상성표는 이 앱이 정리한 일반적인 LoL 전략 지식(포킹 > 쌍포/보호 > 돌진 > 포킹의 삼각관계 등)을 고정된 표로 넣어둔 것뿐입니다. 실제 게임은 아이템/스킬 숙련도/시야 등 훨씬 많은 변수로 갈리므로 참고용으로만 봐주세요.
