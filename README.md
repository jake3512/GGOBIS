# GGOBIS (꼬비스) — LoL 라인 카운터 / 픽 추천 (다중 소스)

리그 오브 레전드 전적 사이트 **6곳**(op.gg, u.gg, lolalytics, Mobalytics, DeepLoL, lol.ps)의 데이터를 요청이 들어올 때마다 실시간으로 가져와 합쳐서 보여주는 웹 앱입니다. 자체 DB나 데이터 수집 파이프라인이 없습니다 — 매 조회가 곧 각 사이트에 대한 실시간 조회입니다. 주로 모바일에서 쓰는 걸 전제로 화면을 맞췄습니다(뷰포트 자동 대응, 더블탭 확대/텍스트 선택 비활성화 — 아래 "모바일 UI" 참고).

- **라인 카운터**: 챔피언 + 라인을 고르면 그 조합을 상대하기 좋은/나쁜 챔피언과 승률을 여러 사이트에서 가져와 보여줍니다.
- **픽 추천**: 실제 픽창처럼 **우리팀 5칸 + 상대팀 5칸, 총 10칸**짜리 입력판에서 내가 픽할 포지션을 고르고 아는 만큼만 채우면 됩니다. 결과는 세 가지를 따로 보여줍니다. (독립된 "바텀 듀오 시너지" 탭은 모바일 조작 편의성 개선 과정에서 제거했습니다 — 탭 하나를 통째로 쓸 만큼 자주 찾는 기능이 아니었고, 원거리 딜러+서포터 듀오 시너지 데이터는 이 픽 추천 탭 안(아래 1번의 "듀오 시너지 데이터"와 3번의 "실측 데이터 기반 전체 시너지")에서 그대로 계속 쓰입니다.)
  1. **내 픽 추천**: 실제 승률은 10칸 중 **상대의 내 포지션 칸**(라인 카운터 데이터)과, 서포터를 픽할 때는 **우리팀 원거리 딜러 칸**(듀오 시너지 데이터)에서만 가져옵니다 — 이 사이트들에 다른 포지션 상대와의 실측 승률 데이터 자체가 없기 때문입니다(카운터 페이지는 항상 같은 라인끼리만 존재). 둘 다 있으면 두 지표를 평균 내 "둘 다 좋은 픽"도 따로 보여줍니다.

     **순위에는 상대팀 전체가 반영됩니다.** 승률은 여전히 내 라인 상대(±듀오 파트너) 매치업에서만 가져오지만, 순위를 매길 때는 상대팀에 채워둔 **다른 포지션 챔피언들도** 함께 봅니다 — Riot 공식 챔피언 태그(`Tank`/`Fighter`/`Assassin`.../`info.defense`)만으로 판단하는 두 가지 신호만 씁니다: 상대팀에 탱커가 없으면 암살자 후보에게, 상대팀이 전사/암살자 위주(다이브형)면 튼튼한(탱커 태그 또는 방어력 6 이상) 후보에게 가산점을 줍니다(`scoreEnemyCompFit`, `src/lib/teamComp.ts`). CC기·이니시 성향처럼 Riot이 공식 정적 데이터로 안 주는 항목은 여기에도 넣지 않았습니다. 이 가산점은 실제 승률 대비 **25%의 낮은 비중**(`PICK_REAL_WEIGHT=0.75` / `PICK_FIT_WEIGHT=0.25`)만 차지해서, 승률 격차가 뚜렷한 픽의 순서를 뒤집는 일은 없고 비슷한 후보들 사이에서만 순위를 조금 흔듭니다. 적용된 후보에는 **"상대팀 조합에 적합"** 배지가 붙습니다. 상대팀 챔피언이 아직 하나도 안 채워져 있으면 이 가산점은 모두에게 중립(0.5)이라 순위에 아무 영향이 없습니다 — 채울수록 반영되는 정보가 늘어납니다.

     **상위 5개는 실제 스킬 조합까지 봅니다.** 위 태그 기반 가산점 위에, 표본이 있는 상위 5개 후보에 한해 Data Dragon의 챔피언별 상세 데이터(`.../data/{locale}/champion/{slug}.json` — 패시브+Q/W/E/R의 이름·설명이 담긴 공식 엔드포인트)를 후보와 상대팀 전원에 대해 조회해서 실제 스킬 구성으로 한 번 더 순위를 다듬습니다(`applySkillFitBonus`, `src/lib/championSkills.ts`). 예를 들어 상대팀에 하드 CC가 하나도 없으면 기동성 스킬을 가진 후보에게, 상대팀에 탈출기(기동성/보호막/회복)가 하나도 없으면 하드 CC를 가진 후보에게 가산점을 줍니다. **주의**: Riot은 "이 스킬은 기절이다" 같은 구조화된 분류를 공식적으로 제공하지 않습니다 — 이 태그는 스킬 설명 텍스트(공식 원문)를 "기절"/"속박"/"돌진"/"보호막" 같은 한국어 게임 용어로 키워드 매칭해서 추론한 것이라, 문구가 특이한 스킬은 놓치거나 잘못 분류될 수 있는 휴리스틱입니다. 표본이 있는 상위 5개에만 적용되는 이유는 위 다른 상위-N 전용 기능(파워 커브, 빌드)과 같습니다 — 후보 전체(20~40명)마다 챔피언 하나씩 별도 요청을 보내는 게 낭비이기 때문입니다. 챔피언 풀(숙련도 티어) 기능이 켜져 있으면 이 재정렬은 절대 티어 순서를 건드리지 않고 같은 티어 안에서만 순위를 조정합니다.
  2. **실측 데이터 기반 전체 시너지**: 양 팀이 같은 라인에 서로 챔피언을 채워둔 모든 라인의 실제 매치업 승률, 그리고 우리팀 원거리 딜러+서포터가 둘 다 채워져 있으면 그 듀오의 실제 시너지 승률을 — 지금까지와 똑같이 실시간 스크래핑한 진짜 숫자로 — 우리 시점 승률로 환산해서 보여줍니다. 각 라인/듀오를 평균 낸 "종합 점수"도 함께 제공합니다.

     **라인전 세부지표**: 위 라인 매치업 각각에, lol.ps의 전용 1:1 비교 엔드포인트(`https://lol.ps/api/versus/stats.json?lane={n}&champion1={ally}&champion2={enemy}` — champSummary/graphs.json과는 완전히 별개의 API로, 사용자가 Network 탭에서 직접 찾아준 요청)에서 가져온 15분 골드/경험치/CS 차이(아군 기준, 양수면 아군 우위), 15분 이전 솔로킬 수, 최대 레벨 리드, 6레벨 우위 비율, 표본 게임 수를 함께 보여줍니다(`getVersusStats`, `src/lib/sources/lolps.ts`). 이 엔드포인트는 챔피언 하나의 페이지가 아니라 **두 챔피언을 동시에 지정**해야 하는 진짜 1:1 비교 API라서, 이미 아군/적군이 둘 다 정해진 라인에서만 자연스럽게 쓸 수 있습니다(추천 후보 목록처럼 상대가 여럿인 곳엔 안 붙였습니다 — 후보마다 별도 요청이 필요해서). 응답에 있는 KDA·데미지/분·시야점수·전체 승률 같은 필드는 라인전(15분 이전) 지표가 아니라 게임 전체 지표라서 의도적으로 안 씀. `region`/`tier` 파라미터는 graphs.json과 같은 이유로 고정값(`LOLPS_REGION=0`/`LOLPS_TIER=2`)을 보내고, `version`은 매 요청마다 실제 현재 버전 번호를 알아내서 함께 보냅니다(`getCurrentLolpsVersion`) — 처음엔 op.gg의 `patch`처럼 생략했었는데, 실제로는 그러면 거의 빈 데이터가 돌아온다는 게 확인돼서 고쳤습니다. 자세한 경위는 아래 lol.ps 표 항목 참고. 라인마다 이 `getVersusStats` 조회와 그 라인의 6개 소스 카운터 집계 조회는 서로 무관해서, 순차로 기다리는 대신 동시에 시작해두고 필요할 때 결과를 기다리는 방식으로 처리합니다(둘 다 실제로 순서를 지킬 필요가 없는데도 처음엔 순차 `await`로 짜여있던 걸 나중에 발견해서 고침).
  3. **챔피언 특성 기반 조합 분석**: 위와 달리 **승률 데이터가 전혀 없어도** 계산되는 보조 지표입니다. Riot Data Dragon이 공식으로 발표하는 챔피언 태그(전사/탱커/마법사/암살자/서포터/원거리 딜러)와 공격형/마법형 능력치(`info.attack`/`info.magic`, 0~10점)만 이용해서, 채워진 아군/적군 챔피언들의 역할군 분포·프론트라인(탱커) 유무·물리 대 마법 데미지 비중을 보여줍니다. 실제 승률 통계가 아니라 참고용 체크리스트라는 점, 그리고 CC기 보유량·이니시 성향처럼 Riot이 공식 정적 데이터로 발표하지 않는 항목은 넣지 않았다는 점을 분명히 표시해뒀습니다. (오프라인 폴백 챔피언 목록에는 `info` 값이 없어서, Data Dragon에 접속 못 하는 환경에서는 데미지 비중 없이 태그 정보만 나옵니다.) — 1번의 "상대팀 조합에 적합" 가산점(`scoreEnemyCompFit`)도 같은 태그/능력치 데이터를 쓰지만 용도가 다릅니다: 이건 **이미 채워진 두 팀 조합 자체**를 요약해서 보여주는 지표고, 1번의 가산점은 **아직 안 뽑은 내 후보 하나하나**가 상대팀과 얼마나 맞는지를 순위에 반영하는 용도입니다. `analyzeTeamComp`/`scoreEnemyCompFit` 둘 다 `src/lib/teamComp.ts`에 있습니다.

     **원거리 딜러 공격 속성 세분화**: 같은 조합 분석 카드 안에, 채워진 챔피언 중 원거리 딜러(Marksman 태그) 챔피언마다 **치명타/공속·공속·퍼센트 데미지·치명타 데미지·주문검** 다섯 가지 공격 속성 중 해당하는 걸 보여줍니다. 위 나머지 항목(태그 분포·프론트라인·데미지 비중)과 달리 **이건 Data Dragon 같은 공식 API에 없는 값**이라 — "이 챔피언은 치명타형이다" 같은 필드는 어디에도 없음 — 이 앱이 직접 정리해서 하드코딩한 참고용 분류표입니다(`src/lib/adcArchetype.ts`), `compConcepts.ts`의 `CONCEPT_MATCHUPS`/`CONCEPT_PILOT_TIPS`(공식 데이터 아닌 일반 LoL 지식을 정적으로 넣어둔 참고표)와 같은 종류입니다. 바텀 라인에서 흔히 보이는 핵심 챔피언 풀(26명)만 커버했고, 표에 없는 마크스맨은 조용히 빠집니다(억지로 분류하지 않음) — 최신 챔피언이나 이 표에 없는 챔피언, 그리고 패치로 실제 빌드 메타가 바뀐 경우 최신 정보와 다를 수 있다는 점을 화면에도 명시했습니다. **"주문검"**은 나머지 네 속성(치명타·공속·퍼센트 데미지 계열)과 달리 트리니티 포스/신화 각성기 같은 온힛·하이브리드 아이템 위주로 딜을 넣는 빌드 방향을 가리킵니다(코르키·이즈리얼·스몰더) — 이 앱 사용자가 직접 최신 메타 기준으로 분류/수정해준 값입니다. 별도로 **"빌드 유동적"** 배지는 바루스·진처럼 매치업/메타에 따라 실제 빌드 방향이 자주 바뀌는 챔피언에 붙습니다 — 위 다섯 속성과는 독립적인 꼬리표입니다. `analyzeTeamComp`가 이 값도 함께 반환하도록 확장했습니다(`TeamCompAnalysis.adcArchetypes`).

     **탱커(탱커 서포터 포함) 생존 방식 세분화**: 같은 방식으로, 채워진 챔피언 중 탱커(Tank 태그) 챔피언마다 **보호막·방어력·데미지 감소·회복·체력** 다섯 가지 생존 방식 중 실제 킷에 해당하는 걸 보여줍니다(`src/lib/tankArchetype.ts`) — 위 원거리 딜러 속성과 완전히 같은 성격(공식 데이터 아닌 이 앱의 참고용 분류)의 하드코딩 데이터입니다. 탱커 서포터를 따로 목록에 안 넣은 이유는, Riot이 레오나·브라움·나서스·알리스타 같은 탱커형 서포터에 이미 `Tank` 태그를 함께 붙여두기 때문에 `Tank` 태그 하나로 순수 탱커와 탱커 서포터가 같이 잡히기 때문입니다. 핵심 탱커 풀(17명)만 커버했고, 킷을 봐도 이 다섯 범주 중 뚜렷하게 해당하는 게 없는 챔피언(아무무·세주아니 등)은 억지로 채우지 않고 표에서 뺐습니다. 한 챔피언이 여러 속성에 동시에 해당할 수 있습니다(예: 몬드는 체력+회복, 말파이트는 보호막+방어력). `analyzeTeamComp`가 이 값도 함께 반환합니다(`TeamCompAnalysis.tankArchetypes`).

     **브루저 딜/생존 방식 세분화**: 같은 방식으로, 채워진 챔피언 중 브루저(Fighter 태그) 챔피언마다 **흡혈·공속·탱킹·유틸** 네 가지 브루저 유형 중 실제 킷에 해당하는 걸 보여줍니다(`src/lib/bruiserArchetype.ts`) — 위 두 항목과 완전히 같은 성격의 하드코딩 참고 데이터입니다. 위 원거리 딜러/탱커와 다른 점 하나: `Fighter` 태그는 정글 암살자(렝가 등)·서포터(쓰레쉬)·마법사 하이브리드(다이애나·엘리스)처럼 "브루저"라 부르기 애매한 챔피언까지 폭넓게 걸쳐 있어서, 태그 하나로 대상을 다 잡는 대신 실제로 브루저로 통하는 핵심 챔피언 풀(34명)만 표에 담았고 나머지 Fighter 태그 챔피언은 표에 없는 것과 동일하게 조용히 빠집니다. "흡혈"은 탱커 항목의 "회복"(고정/비율 체력 회복 스킬)과는 구분해서, 입힌 피해에 비례해 체력을 되찾는 흡혈/옴니뱀프 계열 킷·빌드에만 붙였습니다(예: 워윅·올라프·트런들처럼 킷 자체가 흡혈을 명시하는 챔피언). **"유틸"**은 나머지 세 속성(딜을 넣거나 버티는 방식)과 달리, CC·이동기처럼 전투 판을 바꾸는 능력이 킷의 핵심인 경우에 붙습니다(예: 잭스·바이·헤카림) — 사용자가 직접 분류해준 값입니다. `analyzeTeamComp`가 이 값도 함께 반환합니다(`TeamCompAnalysis.bruiserArchetypes`).

     **조합 컨셉(돌진·포킹·쌍포·한타·스플릿)**: 3번 항목 바로 아래, 같은 위치에 뜨는 별도 카드입니다. 채워진 아군/적군 각각을 다섯 가지 잘 알려진 LoL 조합 컨셉으로 채점합니다(`src/lib/compConcepts.ts`).
     - **돌진/이니시**: 갭클로저나 하드 CC를 가진 전사/암살자/탱커가 여럿
     - **포킹**: 사거리 900+ 스킬(Q/W/E, 공식 `range` 수치 기준)을 가지면서 기동성은 없는 마법사/원거리 딜러가 여럿
     - **쌍포/보호**: 방어력 낮은 마법사·원거리 딜러(캐리 역)와 보호막/회복/CC를 가진 서포터(보호 역)가 **둘 다** 있어야 인정
     - **한타**: 하드 CC를 가진 탱커/서포터/마법사가 여럿 (진형을 잡고 5:5를 거는 그림)
     - **스플릿 푸시**: 방어력 5 이상인 전사가 여럿 (혼자서도 버티는 듀얼리스트)

     각 컨셉은 몇 명이 해당하는지("N/채워진 인원") 그대로 보여주고, 과반(2명 이상, 쌍포는 위 두 역할이 모두 있을 때만)이 맞으면 "지배적 컨셉"으로 표시합니다. 양 팀 다 지배적 컨셉이 있으면 **포킹 > 쌍포/보호 > 돌진 > 포킹**(잘 알려진 삼각 상성)과 한타-스플릿의 관계 등 몇 가지 정적 참고 문구도 함께 보여줍니다(`CONCEPT_MATCHUPS`) — 이건 실측 승률이 아니라 **일반적인 LoL 전략 지식**이라는 걸 화면에도 명시했습니다. 스킬 사거리/CC/기동성 신호는 `championSkills.ts`를 그대로 재사용하므로 그쪽의 키워드-매칭 한계(정확한 분류가 아니라 추론)도 똑같이 적용됩니다. 픽 추천 순위(1번)에는 반영되지 않고, 이미 채워진 조합을 설명하는 용도로만 씁니다.

     **컨셉별 플레이 팁**도 지배적 컨셉이 잡히면 카드 안에 같이 뜹니다. 우리팀 카드에는 그 컨셉을 "어떻게 플레이할지"(예: 포킹형이면 "정면 교전을 피하고 사거리 밖에서 스킬로 지속적으로 딜을 넣으세요"), 상대팀 카드에는 그 컨셉을 "어떻게 상대할지"(예: 상대가 돌진형이면 "핵심 캐리는 항상 팀원 뒤에, 플래시·보호기를 아끼세요") 팁을 2~3개씩 보여줍니다. 위 상성표와 마찬가지로 **실측 데이터나 API에서 오는 값이 아니라, 이 앱이 정리해서 고정으로 넣어둔 일반적인 LoL 공략 지식**입니다(`CONCEPT_PILOT_TIPS`/`CONCEPT_COUNTER_TIPS`, `src/app/page.tsx`) — 그래서 서버가 아니라 프론트엔드에만 있고 API 응답에는 포함되지 않습니다(컨셉 라벨처럼 정적 텍스트라 서버를 왕복할 이유가 없습니다).

     **챔피언 선택 화면의 CC(하드 크라우드 컨트롤) 표시**: 위 조합 컨셉/픽 추천 순위 보정에 이미 쓰던 `championSkills.ts`의 `hasHardCC`(Data Dragon 공식 스킬 설명 텍스트에서 "기절"/"속박"/"침묵"/"매혹"/"공포"/"도발"/"수면"/"제압"/"공중으로 띄워"/"이동 불가" 같은 키워드로 추론한 값 — 키워드 매칭 휴리스틱이지 Riot 공식 분류는 아님, 위 답변 참고)를 챔피언 선택 화면(10칸 입력판) 자체에도 노출했습니다. 슬롯에 챔피언을 넣으면 이름 옆에 작은 점이 붙어서 빨간 점=하드 CC 보유, 빈 점=CC 없음, 점선 회색 점=아직 확인 중이거나 조회 실패(Data Dragon 응답 없음 등)를 나타냅니다 — "없음"과 "모름"을 같은 표시로 뭉치지 않도록 세 가지 상태를 구분했습니다. 우리팀/상대팀 컬럼 아래에는 **CC 보유 챔피언 — 우리팀 N/채워진 인원 · 상대팀 M/채워진 인원** 합계도 함께 보여줍니다(`ccInfo`, `src/app/api/pickadvice/route.ts`). 별도 네트워크 요청은 추가되지 않았습니다 — 조합 컨셉 분석이 이미 채워진 챔피언 전원의 스킬 데이터를 Data Dragon에서 가져오고 있어서(`fetchAbilitiesMap`), 그 결과를 재사용만 한 것입니다.

  나머지 칸(예: 서로 채워지지 않은 라인)은 지금 당장은 위 세 계산 어디에도 쓰이지 않는, 더 많은 사이트를 연동하면 활용할 수 있도록 미리 마련해둔 자리라는 걸 화면에도 명시해뒀습니다. 1번 시너지 추천(정확한 페어 하나에 대한 실제 승률)이 서포터를 픽할 때만 제공되는 이유는, 확인된 사이트 데이터가 "원거리 딜러 → 시너지 좋은 서포터" 방향의 목록만 있고 반대 방향이나 탑/정글/미드의 팀 시너지 데이터는 확인된 소스가 없기 때문입니다 — 이 제약은 그대로지만, 아래 "전 포지션 시너지 교집합" 기능으로 다른 포지션에도 (더 거친 형태로) 반영했습니다.

  **전 포지션 시너지 교집합**: op.gg 등의 "시너지" 페이지가 원래 ADC 전용이 아니라 포지션 세그먼트(`/synergies/{position}`)를 받는다는 걸 활용해서, `getBotDuoCandidates`/`getBotDuoSynergy`를 ADC 전용에서 모든 포지션으로 일반화했습니다(`src/lib/sources/genericSource.ts`, `registry.ts`). 이걸로 "우리팀에 이미 채워둔 챔피언 여러 명과 각각 시너지 좋은 챔피언의 교집합"을 계산합니다: 채워진 아군 한 명 한 명에 대해 그 챔피언 자신의 포지션 기준 시너지 파트너 상위 20명을 실제 스크래핑 데이터로 가져온 뒤(`computeAllySynergyScores`), 후보 챔피언이 몇 명의 아군과 겹치는지(`matchCount`/`outOf`)와 겹친 아군들에 대한 평균 실제 승률을 계산합니다 — **전원과 겹치면(matchCount === outOf) 진짜 교집합**이고, 일부만 겹쳐도 몇 명과 겹치는지 그대로 보여줍니다(빈 결과를 조용히 숨기지 않음). "라인전 유리한 픽"/"시너지 좋은 픽" 두 목록 모두에 **우리팀 N명 중 M명과 시너지 좋음 (평균 X%)** 배지로 표시되고, 순위에도 반영됩니다: 기존에는 실제 라인전 승률 75% + 상대 조합 태그 휴리스틱 25%였던 가중치를, 실제 라인전 승률 65% + 상대 조합 태그 휴리스틱 15% + **이 실측 아군 시너지 데이터 20%**로 재분배했습니다(`PICK_REAL_WEIGHT`/`PICK_ENEMY_FIT_WEIGHT`/`PICK_ALLY_SYNERGY_WEIGHT`, `rerankPicks`) — 태그 휴리스틱보다 실측 데이터에 더 높은 비중을 주되, 여전히 직접적인 라인전 승률이 압도적 1순위입니다. **알려진 한계**: 5명 전체가 함께 나온 매치 데이터가 아니라 "챔피언 하나당 시너지 파트너"를 아군별로 독립적으로 조회해서 겹치는 걸 찾는 방식이라, 진짜 5:5 조합 승률과는 다릅니다(원본 매치 데이터 없이는 계산 불가능 — README 앞부분 "실제 매치 기록" 관련 논의 참고). 상위 20명 안에 들지 않으면 매치로 안 잡히므로, 표본이 적은 조합은 실제로 시너지가 있어도 놓칠 수 있습니다.

  **파워 커브(초반/후반 성향)**: 1번 "내 픽 추천" 목록의 상위 5개 후보에는 lol.ps의 분당 승률 그래프(`/api/champ/{id}/graphs.json`)를 추가로 붙여서 "초반 몇 %, 후반 몇 %"를 함께 보여줍니다. 둘의 차이가 크면 "(초반형)"/"(후반형)" 표시도 붙습니다. 이 데이터는 op.gg 등의 카운터/승률 데이터와는 별개로, lol.ps만 제공하는 값입니다. 사용자가 브라우저에서 HAR(전체 네트워크 캡처)을 떠서 찾아준 덕분에 발견한 엔드포인트입니다. `tier`/`region`은 고정값을 보내고 `version`은 매 요청마다 실제 현재 버전을 알아내서 보냅니다(아래 lol.ps 표 항목 참고) — 그리고 champSummary와 같은 한계로 이 값도 그 챔피언 자신의 주 라인 데이터만 주기 때문에, 요청한 포지션과 일치할 때만 붙습니다. 표본이 많은 상위 5개에만 붙는 이유는 후보 목록 전체(20~40명)에 대해 매번 추가로 그래프를 조회하는 게 낭비이기 때문입니다.

  **파워 커브·라인전 세부지표를 순위에도 반영**: 위 두 신호(팀 파워 커브, 라인전 세부지표)는 처음엔 표시 전용이었는데, 이제 상위 5개 후보의 순위 자체에도 반영됩니다(`refineTopWithPowerCurveAndLaning`, `src/app/api/pickadvice/route.ts`, `refineTopWithSkillFit` 다음 단계로 실행돼서 최종 순위를 정함). 새 최상위 가중치를 따로 추가하는 대신(그러면 `PICK_REAL_WEIGHT`/`PICK_ENEMY_FIT_WEIGHT`/`PICK_ALLY_SYNERGY_WEIGHT`를 또 재분배해야 함), 두 신호를 개념적으로 가장 가까운 기존 가중치 슬롯에 **블렌딩**해 넣는 방식을 택했습니다:
  - **팀 파워 커브 적합도**: 이미 채워진 아군 라인들의 팀 파워 커브가 가장 강한 구간(초반/중반/후반, `teamPeakPhase`)에 후보 자신의 그 구간 승률이 얼마나 부합하는지를 0.5~1.0 스케일로 변환(`phaseFitScore`)해서, `allySynergyFit`에 **30%**(`POWER_CURVE_TEAM_FIT_BLEND`) 비중으로 섞습니다 — "우리팀 계획에 맞는 픽"이라는 성격이 아군 시너지 적합도와 같은 결이라 그 슬롯에 넣었습니다.
  - **라인전 세부지표 적합도**: "라인전 카운터" 추천(내 라인 상대가 정해져 있는 경우)에 한해, 후보와 그 상대의 실제 15분 골드 차이(`versus/stats.json`)를 0.5~1.0 스케일로 변환(`laningFitScore`, ±2000골드를 대략 한 등급 스윙으로 간주 — 별도 근거 데이터가 없어 보수적으로 잡은 값)해서, 실제 승률(`goodness`) 항목에 **25%**(`LANING_STATS_BLEND`) 비중으로 섞습니다 — 이건 실측 매치업 데이터라 태그 기반 적합도가 아니라 실제 승률 쪽에 더 가깝다고 판단했습니다. "시너지 좋은 픽"(바텀 듀오 시너지)은 특정 상대 라이너가 없어서 이 절반은 건너뜁니다.

  최상위 가중치(`PICK_REAL_WEIGHT=0.65`/`PICK_ENEMY_FIT_WEIGHT=0.15`/`PICK_ALLY_SYNERGY_WEIGHT=0.2`)는 그대로 유지되고, 두 신호는 그 안에서만 순위를 조금 더 흔듭니다. `combinedPicks`("둘 다 좋은 픽")는 이번엔 건드리지 않았습니다 — counterPicks/synergyPicks가 이미 반영된 뒤의 `winRate`/`compFit`/`allySynergyFit`을 그대로 평균만 내는 구조라 새 신호도 간접적으로는 섞여 들어가지만, 별도 블렌딩 로직을 추가하진 않았습니다.

  **버그 수정 — 파워 커브도 라인 불일치 캐비어트가 빠져있었음**: 위 도입 당시, `getPowerCurve()`가 반환하는 `actualPosition`(이 수치가 실제로 어느 라인 기준인지)을 한 번도 확인하지 않고 `earlyWinRate`/`lateWinRate`를 그대로 붙이고 있었습니다 — `annotateWithBuild`/`computeTeamPowerCurve`는 이미 라인이 다르면 `laneNote`로 표시하는데, 이 함수만 빠뜨린 채였습니다. 예를 들어 원딜 추천에서 상위 후보의 lol.ps 주 라인이 정글이면, 그 정글 데이터를 아무 경고 없이 "초반/후반 승률"로 보여주고 있었던 것 — 바로 아래 빌드 카드는 정상적으로 "⚠ 정글 라인 데이터만..." 경고를 붙이는데도 파워 커브 배지만 조용했습니다. `powerCurveLaneNote` 필드를 추가해서 같은 방식으로 고쳤습니다.

  **분당 승률 상세(스파크라인 + 표)**: "파워 커브에 대한 더 세부적인 정보를 보여달라"는 요청으로 추가했습니다. 위 "초반/중반/후반" 세 구간 평균은 `getPowerCurve()`가 내부적으로 이미 갖고 있던 lol.ps `graphs.json`의 실제 분당(3~33분, 약 31개 포인트) 승률 배열(`PowerCurve.points`, `src/lib/sources/lolps.ts`)을 3등분해서 평균 낸 값인데, 지금까지는 이 원본 31개 포인트를 `getPowerCurve()` 바깥으로 아예 넘겨주지 않고 평균 세 개만 반환하고 있었습니다 — 새로 스크래핑을 늘린 게 아니라 이미 가져와 놓고 버리던 값을 `PowerCurveWithLane.points`로 그대로 노출한 것입니다. 3구간 평균만으로는 예를 들어 "10분에 강하고 25분에 다시 강한데 그 사이엔 약한" 챔피언도 애매한 "중반형"으로 뭉개져 버리는데, 원본 포인트를 보면 그 굴곡이 그대로 드러납니다. 파워 커브가 뜨는 모든 곳(라인 카운터/픽 추천의 카운터·시너지 후보, 픽 추천의 팀 파워 커브 라이너별 상세, 조합 비교 탭의 로스터 파워 커브)에 "분당 승률 상세" 접이식 섹션으로 추가했고, 안에는 순수 인라인 SVG로 그린 작은 스파크라인(외부 차트 라이브러리 없이 `<polyline>` 하나, 50% 기준선 점선 포함, `PowerCurveDetails`, `src/app/page.tsx`)과 분 단위 정확한 수치 31개가 함께 뜹니다. 서버 응답 필드명은 각 위치의 기존 컨벤션을 그대로 따랐습니다(`PickEntry`/`CounterEntry`는 `powerCurvePoints`, `LanerPowerCurve`/`RosterPowerCurveEntry`도 `powerCurvePoints`) — 전부 `earlyWinRate`/`lateWinRate`가 이미 있던 바로 그 자리에 나란히 추가된 옵셔널 필드라 기존 응답 구조를 깨지 않습니다.
- **빌드 추천** (룬/스펠/아이템/스킬 순서): lol.ps 챔피언 페이지에 이미 내장돼 있던 같은 `champSummary` 블록에서 카운터 데이터와 함께 뽑아냅니다 — 별도 네트워크 요청이 추가로 필요 없습니다. 세 곳에서 볼 수 있습니다.
  1. **빌드 탭**: 챔피언+라인만 고르면 룬(메인/서브 트리+개별 룬), 스펠 조합, 시작 아이템, 핵심 3아이템, 전체 빌드 순서(신발 포함), 스킬 마스터리 순서, 레벨 1~15 스킬업 순서를 각각의 승률/표본 수와 함께 보여줍니다.

     **최소 3가지 종류의 빌드**: "빌드 탭에서 빌드를 최소 3가지는 보여달라"는 요청으로, lol.ps 카드 하나 + DeepLoL 카드 하나(둘 다 딱 1개씩)였던 예전 화면을 늘렸습니다. deeplol의 `build_lst`는 원래부터 (`champion_id`+라인당) **여러 개의 실제 랭크된 빌드 변형**을 배열로 주는데, 지금까지는 그중 `build_lst[0]`(가장 많이 쓰인 빌드) 하나만 쓰고 나머지는 그냥 버리고 있었습니다 — 새로 만든 로직이 아니라, 이미 스크래핑해오던 응답 안에 있었지만 안 쓰고 있던 실제 데이터를 꺼내 쓴 것입니다. `getChampionBuildVariants(championId, position, limit)`(`src/lib/sources/deeplol.ts`)가 `build_lst`를 `limit`개까지 그대로 슬라이스해서 각각을 기존 `ChampionBuild` 형태로 변환해 돌려줍니다(변환 로직 자체는 예전 `getChampionBuild`와 동일 — `mapBuildVariant`로 분리해서 재사용). lol.ps는 애초에 랭크된 변형 목록이라는 개념 자체가 없어서(챔피언 페이지 하나에 빌드가 하나) 항상 최대 1개만 돌아옵니다. `/api/build`에 새 `variants` 쿼리 파라미터(예: `&variants=3`)를 넣으면 응답이 기존 단일 `BuildResult` 객체 대신 `{ builds: BuildResult[] }` 배열로 바뀝니다 — 이 파라미터를 안 보내는 기존 호출(라인 카운터 탭의 배경 빌드 조회)은 예전과 똑같은 단일 객체 응답을 그대로 받아서 회귀가 없습니다. 빌드 탭은 lol.ps·DeepLoL 둘 다 `variants=3`으로 요청해서, 화면엔 보통 **lol.ps 1개 + DeepLoL 최대 3개 = 최대 4개**의 빌드 카드가 뜹니다(챔피언에 따라 DeepLoL 쪽 실제 변형 수가 3개보다 적을 수도 있음 — 있는 만큼만 보여주고 억지로 채우지 않음). 각 카드에는 "N번째로 인기 있는 빌드"(`BuildCard`의 `variantLabel` prop, `buildVariantLabel()`, `src/app/page.tsx`) 라벨이 붙어서 어느 변형인지, 그리고 여전히 서로 다른 소스/변형끼리 승률을 합산하지 않는다는 걸 명시합니다.

     **아이템 2개 이상 다른 빌드만 골라서 보여줌**: 위 기능을 쓰다 보니 deeplol의 `build_lst`가 종종 거의 똑같은 핵심 아이템에 신발이나 상황용 아이템 하나만 바꾼 항목을 연달아 여러 개 갖고 있어서, `build_lst[0..2]`를 그대로 잘라 쓰면 "3가지 빌드"라고 해놓고 실제로는 서로 거의 구분이 안 되는 경우가 있었습니다. "아이템이 2개 이상 다른 빌드를 보는 기능을 만들어달라"는 요청으로, `getChampionBuildVariants`가 이제 `build_lst`를 앞에서부터 순서대로 슬라이스하는 대신 **전체를 훑으면서** 핵심 아이템 구성이 이미 고른 빌드들과 최소 2개 이상 다른 항목만 채택합니다(`itemSetDiffCount`, 새 파일 `src/lib/buildDiff.ts` — 두 빌드의 핵심 아이템을 집합으로 보고 서로만 갖고 있는 아이템 개수를 더한 대칭차, 구매 순서는 무시). 가장 인기 있는 빌드(`build_lst[0]`)는 항상 무조건 먼저 채택되고, 그 뒤부터는 이미 채택된 모든 빌드와 2개 이상 달라야 추가됩니다 — 그래서 `build_lst`가 비슷한 변형만 여럿이고 뒤쪽에 가서야 진짜 다른 구성이 나오는 챔피언이면, 그 뒤쪽까지 계속 훑어서 찾아냅니다(앞 3개만 보지 않음). 진짜로 다른 변형이 `limit`개보다 적게 있으면 그만큼만 반환하고 억지로 채우지 않습니다(라인 카운터 탭처럼 `limit=1`로 부르는 기존 호출은 이 로직이 있어도 여전히 `build_lst[0]` 그대로라 회귀 없음 — `selected.length === 0`일 때 무조건 채택하는 첫 항목이 그대로 그 값이기 때문). 화면에는 DeepLoL의 2번째/3번째 이후 카드마다 "(핵심 아이템 N개 다름)"이 라벨에 함께 붙어서(`itemSetDiffCount`를 클라이언트에서도 그대로 재사용, `src/app/page.tsx`), 실제로 몇 개가 다른지 그 자리에서 바로 보입니다 — 서버가 이미 2개 미만인 조합은 걸러냈으니 이 숫자는 항상 2 이상입니다.
  2. **라인 카운터 결과**: 조회한 기준 챔피언의 빌드 카드가 카운터 목록 아래에 자동으로 같이 붙습니다.
  3. **픽 추천 결과**: "내 픽 추천"/"시너지 좋은 픽" 상위 5개 후보 각각에, 룬 키스톤+스펠+핵심 아이템만 담은 축약 카드가 **lol.ps·DeepLoL 두 소스 모두** 따로따로 붙습니다(각각 "lol.ps"/"DeepLoL" 라벨로 구분 — 두 소스를 합산하지 않는다는 원칙은 그대로). 원래는 lol.ps 하나만 붙어있었는데, 라인 카운터 결과/빌드 탭엔 이미 있던 DeepLoL 빌드가 여기만 빠져 있어서 똑같이 추가했습니다(`annotateWithDeeplolBuild`, `src/app/api/pickadvice/route.ts`) — DeepLoL은 lol.ps와 달리 라인이 진짜로 구분돼 있어서(주 라인 한정 아님) 라인 불일치 처리가 아예 필요 없습니다. lol.ps 빌드 조회(`annotateWithBuild`)와 DeepLoL 빌드 조회(`annotateWithDeeplolBuild`)는 서로 다른 필드(`build`/`buildDeeplol`)에만 쓰기 때문에 순차 `await` 대신 `Promise.all`로 동시에 실행합니다(처음엔 순차 실행이라 두 조회 시간을 그대로 더해서 기다리고 있었음 — 나중에 발견해서 고침).

  **빌드 데이터를 순위에도 반영**: 두 소스에서 가져온 후보의 실제 추천 핵심 아이템에 상대팀 데미지 타입(물리/마법)에 맞는 방어 아이템이 포함돼 있으면 순위에 소폭 가산점을 줍니다(`applyBuildFitBonus`, 같은 파일). Data Dragon `item.json`이 아이템마다 공식으로 붙여주는 `tags`(예: `"Armor"`, `"SpellBlock"`)를 그대로 씀 — 이 값을 이 앱에서 처음 파싱해서 `DDragonItem.tags`로 노출함(`src/lib/ddragon.ts`). 상대팀의 물리/마법 데미지 비중이 60% 이상으로 확실히 한쪽에 치우쳐 있을 때만(`DAMAGE_MAJORITY_THRESHOLD`) 판단하고, lol.ps·DeepLoL 둘 중 하나라도 그 방향 아이템(방어력 태그면 물리, 마법 저항력 태그면 마법)을 핵심 아이템에 포함하면 `compFit`에 +0.15(`BUILD_DEFENSE_BONUS`)를 더합니다 — `scoreEnemyCompFit`/`applySkillFitBonus`(둘 다 `src/lib/teamComp.ts`)와 같은 "공식 정적 데이터만, 작은 가산점, 1로 클램프" 방식을 그대로 따른 것입니다. 이 가산점도 결국 `compFit`을 통해 기존 `PICK_ENEMY_FIT_WEIGHT`(15%) 비중 안에서만 순위에 영향을 주므로, 실제 승률의 압도적 우위는 여전히 그대로입니다. 이 재정렬(그리고 팀 파워 커브·라인전 세부지표 재정렬)이 서로 다른 곳에서 각자 순위 공식을 따로 베껴 쓰고 있던 걸 발견해서, 공통 `pickRankScore()` 함수 하나로 합쳤습니다 — 나중에 신호를 하나 더 추가할 때 한쪽 재정렬 단계에서만 반영되고 다른 단계에서 사라지는 버그를 막기 위함입니다.

  아이템/스펠/룬 이름·아이콘은 Riot Data Dragon의 공식 정적 데이터(`item.json`/`summoner.json`/`runesReforged.json`)로 채웁니다. 룬 아이콘 경로만 다른 Data Dragon 이미지들과 달리 패치 버전이 안 붙는 `/cdn/img/` 접두사를 쓴다는 걸 확인해서 별도 처리했습니다. champSummary 데이터를 재사용하다 보니 파워 커브/카운터와 완전히 같은 한계를 그대로 물려받습니다: 그 챔피언의 **주 라인 데이터만** 제공되므로 요청한 포지션과 다르면 에러로 표시되고(`getChampionBuild`), 파워 커브와 마찬가지로 픽 추천에서는 표본이 있는 상위 5개 후보에만 조회를 붙입니다. 이 버전 없는 룬 아이콘 경로가 배포 환경에서 `net::ERR_INVALID_RESPONSE`로 깨지는 사례가 실제로 보고돼서, 모든 Data Dragon `<img>`에 `referrerPolicy="no-referrer"`를 붙여뒀습니다(`ChampionIcon.tsx`/`BuildCard.tsx`) — 리퍼러 기반으로 요청을 이상하게 처리하는 CDN 엣지가 원인일 가능성이 있어서 넣은 방어적 조치이며, 이 저장소 환경 자체가 아웃바운드 네트워크가 막혀 있어 직접 재현/검증은 못 했습니다.
- **챔피언을 넣을 때마다 자동으로 다시 조회**: 픽 추천은 처음엔 "픽 추천 받기" 버튼을 눌러야만 조회됐는데, 이제 슬롯에 챔피언을 넣거나 뺄 때마다(포지션 탭을 바꾸거나 챔피언 풀을 바꿀 때도) 자동으로 다시 조회됩니다. 슬롯 하나라도 채워지면 조회 조건이 충족되는(`canRun`) 걸 그대로 재사용해서, 그 상태가 바뀔 때마다 500ms 디바운스 후 `runLookup()`을 실행합니다(`useEffect`, `src/app/page.tsx`) — 여러 슬롯을 빠르게 연달아 클릭해도 마지막 변경 후 500ms간 조용해야 그때 한 번만 조회해서, 클릭할 때마다 6개 사이트를 매번 스크래핑하는 낭비를 막습니다. 느린 응답이 그 사이 시작된 더 최신 요청을 덮어쓰지 않도록 요청마다 증가하는 ID로 최신 여부를 확인하고, 오래된 응답은 도착해도 조용히 버립니다(`requestIdRef`). 버튼은 "지금 바로 새로고침"으로 남겨뒀습니다 — 디바운스를 기다리지 않고 바로 조회하고 싶을 때 씁니다. 라인 카운터/듀오 시너지/빌드 세 탭은 그대로 버튼을 눌러야 조회됩니다(단일/두 슬롯짜리라 자동 조회의 이점이 적다고 판단).

  **버그 수정 — 라인 카운터/빌드 탭의 배경 빌드 조회에는 이 최신 여부 확인이 빠져있었음**: "라인 카운터" 탭의 DeepLoL·lol.ps 빌드 카드, "빌드" 탭의 DeepLoL 카드는 메인 조회가 끝난 뒤 별도로(백그라운드에서) 한 번 더 요청을 보내는 구조인데, 이 두 번째 요청의 응답 처리(`setCounterBuild`/`setBuildResultDeeplol`)에는 `isStale()` 확인이 빠져 있었습니다 — 챔피언 A를 조회한 직후(그 배경 요청이 아직 안 끝난 상태에서) 챔피언 B로 바꿔 다시 조회하면, 나중에 도착한 A의 빌드 카드가 화면엔 B의 카운터 목록 아래 잘못 붙는 경우가 있었습니다. 다른 모든 요청과 똑같이 `isStale()` 확인을 추가해서 고쳤습니다.
- **실제 챔피언 선택 화면 스타일 UI**: 픽 추천 탭의 10칸 입력판을 실제 LoL 챔피언 선택 화면과 비슷한 구조로 바꿨습니다 — 위쪽에 큰 스플래시 아트 미리보기, 그 아래 우리팀(파란 테두리)/상대팀(빨간 테두리) 두 개의 세로 열(각 5칸, 탑→정글→미드→원딜→서폿 고정 순서)로 나눠서 보여줍니다(`.champ-select`, `src/app/page.tsx`). 챔피언을 하나 고를 때마다 그 챔피언의 스플래시 아트(`https://ddragon.leagueoflegends.com/cdn/img/champion/splash/{slug}_0.jpg` — 룬 아이콘과 같은 패치 버전 없는 경로)가 미리보기 영역에 크게 뜹니다. 모바일 화면 폭을 고려해서 실제 클라이언트처럼 좌우 넓은 레이아웃 대신 좁은 두 열로 압축했고, 역할 아이콘 이미지 대신(Data Dragon이 역할 아이콘을 별도로 제공하지 않음) 짧은 텍스트 라벨("탑"/"정글"/...)을 씁니다.
- **팀 파워 커브 (초반/중반/후반)**: 픽 추천 화면에서 우리팀 라인에 채워둔 챔피언들의 lol.ps 분당 승률 그래프를 종합해서, **팀 전체가 어느 구간(초반/중반/후반)에 가장 강한지**와 **각 라이너가 초반형/후반형/균형형 중 어디에 가까운지**를 따로 보여줍니다(`teamPowerCurve`, `computeTeamPowerCurve`, `src/app/api/pickadvice/route.ts`). 각 라이너의 수치는 lol.ps `graphs.json`을 3등분(초반/중반/후반)해서 평균 낸 실제 값이고, 팀 수치는 데이터가 있는 라이너들만 평균 낸 값입니다(빈 라인은 평균에서 제외, 0으로 채우지 않음). "초반형/후반형" 판정은 픽 추천 후보 카드에 이미 쓰던 것과 **같은 ±3%p 기준**(`PowerCurveBadge`)을 재사용합니다. lol.ps는 챔피언의 주 라인 데이터만 주기 때문에, 그 라인이 실제 배정된 포지션과 다르면 **무조건 그대로 보여주면서** 라이너 카드에 안내 문구를 붙입니다(`laneNote`) — 처음엔 빌드 탭과 같은 "그 포지션이 게임의 7% 이상일 때만"(`getLaneShare`) 규칙을 썼는데, `getLaneShare`가 의존하는 `top1LaneId`/`top1LaneRatio` 필드명 자체가 검증된 적 없는 값이라 실제로는 항상 0을 반환해서 **라인이 하나라도 안 맞으면(흔한 경우) 팀 전체가 "데이터를 찾지 못했다"고 뜨는 버그**가 있었습니다 — 배포 후 실제로 이 증상이 보고돼서(`sampledCount`가 항상 0), 이 섹션에서는 그 게이트를 완전히 빼고 항상 보여주는 쪽으로 바꿨습니다. `annotateWithBuild`(픽 추천 후보 카드의 빌드)도 같은 `getLaneShare` 게이트를 쓰고 있어서 같은 버그(오프-라인 후보의 빌드 카드가 예상보다 적게 뜸)가 있었는데, 이제 이 섹션·`/api/build`("빌드" 탭)와 똑같은 방식으로 고쳤습니다 — 게이트를 완전히 빼고, 라인이 다르면 `laneNote`로 표시만 하면서 항상 보여줍니다. `LANE_MISMATCH_MIN_SHARE` 상수와 `getLaneShare` import는 더 이상 이 라우트에서 쓰지 않아 제거했습니다(`getLaneShare` 함수 자체는 `lolps.ts`에 그대로 남아있지만, 이제 이 앱 어디에서도 호출하지 않습니다 — 검증되지 않은 필드명에 의존하는 게이트라 애초에 신뢰하기 어려웠습니다).
- **내 챔피언 풀(숙련도 우선순위)**: 픽 추천 화면 상단의 "내 챔피언 풀" 패널에서 자신이 실제로 플레이하는 챔피언을 **1티어(가장 숙련)/2티어/3티어**로 등록해두면, "내 픽 추천"(1번 항목)의 카운터·시너지·둘 다 좋은 픽 세 목록 전부가 **그 풀 안에서만** 추천되고, 승률 순위보다 **티어 순서가 먼저** 적용됩니다(같은 티어 안에서만 지금까지의 승률 순위로 정렬). 한 챔피언은 한 번에 한 티어에만 속하며, 다른 티어로 다시 등록하면 이전 티어에서는 자동으로 빠집니다. 아무 챔피언도 등록하지 않으면 지금까지처럼 전체 챔피언을 대상으로 추천합니다(기본값). 이 풀은 서버에 저장되지 않고(자체 DB가 없으므로) 브라우저 `localStorage`에만 저장되어 새로고침/재방문에도 유지되지만 기기·브라우저 간에는 공유되지 않습니다. `/api/pickadvice`에 `tier1`/`tier2`/`tier3` 쿼리 파라미터(챔피언 ID 콤마 목록)로 전달되며, 필터링은 클라이언트가 아니라 서버에서 이뤄집니다 — 그래서 파워 커브/빌드 조회(위 두 항목)도 풀 필터링 **이후의** 상위 5개에만 걸려서, 등록 안 한 챔피언 페이지를 불필요하게 조회하지 않습니다.
- 매칭당 표본(게임 수)이 가장 많은 소스를 대표값으로 쓰고, **표본이 많은 순으로 최대 3개 소스**를 함께 보여줍니다.

## 기술 스택

- Next.js (App Router, TypeScript) — 프론트엔드 + API 라우트
- Data Dragon — 챔피언 이름/아이콘 등 정적 데이터 (공식, 무료, 인증 불필요)
- 6개 사이트 실시간 스크래핑 — `src/lib/sources/`

DB도, API 키도 필요 없습니다. `npm install && npm run dev`만으로 뜹니다.

## 동작 원리

1. 챔피언 목록/아이콘은 Data Dragon에서 가져옵니다 (`src/lib/ddragon.ts`, 1시간 캐시, 오프라인이면 `data/fallback-champions.json`으로 대체 — 이 파일은 `fs.readFile(path.join(process.cwd(), ...))`가 아니라 정적 `import`로 불러옵니다. 런타임에 조립한 파일 경로는 Next.js가 추적을 못 해서 Vercel 서버리스 번들에 안 딸려갈 수 있는 잘 알려진 함정이라, 로컬(`next dev`)에서는 멀쩡히 동작하다가 배포 후에만 깨질 수 있습니다).
2. 카운터/듀오를 조회하면 등록된 6개 소스에 **동시에** 요청을 보냅니다 (`src/lib/sources/aggregate.ts`, `Promise.allSettled`로 일부가 실패해도 나머지로 계속 진행).
3. 각 소스는 해당 챔피언의 페이지를 fetch해서, 페이지에 내장된 상태를 파싱해 통계를 뽑아냅니다 (`src/lib/scrape.ts`). 두 가지 임베딩 방식을 지원합니다: 구형 `__NEXT_DATA__`/`__NUXT__` 단일 JSON 블록, 그리고 최신 Next.js App Router가 쓰는 `self.__next_f.push(...)` RSC Flight 스트림(여러 개의 `id:value` 줄로 쪼개져 있고, 값 부분만 따로 JSON 파싱). op.gg가 실제로 후자 방식이라는 걸 실제 페이지 소스로 확인했습니다.
4. 같은 상대 챔피언에 대해 여러 소스가 값을 준 경우, **게임 수가 가장 많은 소스**를 대표값으로 쓰고 상위 3개 소스를 같이 보여줍니다.
5. 같은 조합을 반복 조회할 때 각 사이트에 부담을 덜 주기 위해 소스별로 10분짜리 인메모리 캐시를 씁니다 (서버 재시작/재배포 시 초기화됨 — 영구 저장소가 아닙니다).

## ⚠️ 각 소스 연동 신뢰도 — 반드시 읽어주세요

이 세션은 **6개 사이트 전부에 대한 아웃바운드 네트워크가 막혀 있어** 대부분 직접 검증하지 못했습니다. `src/lib/sources/registry.ts`에 있는 URL 패턴/필드명은 각 사이트 구조에 대한 사전 지식을 근거로 한 최선의 추정치입니다. 소스별 신뢰도:

| 소스 | 신뢰도 | 비고 |

51`에 `timelineWinrates: []`(빈 배열)이라는, 실제 캡처(153/154)와 전혀 다른 낡고 텅 빈 스냅샷이 돌아온다는 게 확인됐습니다 — op.gg의 `patch` 생략과 달리 이 서버는 `version`을 생략해도 "현재 값"으로 대신해주지 않는다는 뜻이라, 뭔가 실제 현재 버전 번호를 알아내서 매번 보내야 하는 문제였습니다.

**최종 해결 — 챔피언 페이지 HTML에서 현재 버전 자동 추출**: 사용자가 챔피언 페이지(`https://lol.ps/champ/{id}`, `version` 파라미터 없이) 전체 HTML을 캡처해준 덕분에 실마리를 찾았습니다. 이 페이지의 SvelteKit 하이드레이션 데이터 안에 두 곳에 버전 정보가 들어있었습니다: (1) 페이지 레벨의 `versionInfo` 배열(`[{versionId:154,description:"26.17",patchDate:"2026-08-26",isActive:true,...},{versionId:153,...},{versionId:152,...}]`, 최신순), (2) 챔피언별 데이터 블록 자신의 `championArguments:{regionId:0,versionId:154,tierId:2,laneId:0}` — **이 요청 자체가 `?version=`을 안 붙였는데도** 서버가 154(=`versionInfo`의 최신 항목과 정확히 일치)로 알아서 채워 응답한 것입니다. 즉 champSummary/빌드용으로 이미 가져오고 있던 바로 그 챔피언 페이지 HTML 안에 "오늘의 진짜 현재 버전"이 그대로 찍혀 있었던 것 — `graphs.json`/`versus/stats.json`은 이 자동 대체를 안 해주지만, 그 값을 구해올 곳은 이미 손 안에 있었던 셈입니다. `extractCurrentVersionId()`가 `championArguments`에서 이 숫자를 정규식으로 뽑아내고, `getCurrentLolpsVersion()`이 이 값을 1시간(패치는 몇 주에 한 번만 바뀌므로) 캐싱해서 `graphs.json`/`versus/stats.json` 요청 모두에 `&version=`으로 매번 실어 보냅니다 — 버전 번호가 하드코딩된 상수가 아니라 매 patch마다 자동으로 갱신되는 구조라 별도 유지보수가 필요 없습니다. 새 네트워크 요청이 추가되는 게 아니라(어차피 champSummary/빌드 조회 때 그 챔피언 페이지를 이미 가져오므로 캐시 히트가 되는 경우가 많음), 정말 처음 조회되는 챔피언이라면 페이지 HTML을 한 번 더 가져오는 정도의 비용만 듭니다. `championArguments` 파싱이 실패해도(사이트 구조 변경 등) 예외를 던지지 않고 `null`을 반환해 `version` 파라미터를 그냥 생략하도록 안전하게 물러납니다 — 이 기능 이전과 같은 정도로만 저하될 뿐, 절대 요청 자체를 깨뜨리지 않습니다. **빌드 추천 데이터도 같은 champSummary 블록 안에 이미 들어있었음**: 룬(`mainRuneCategory`/`mainRune1~4`/`subRuneCategory`/`subRune1~2`), 스펠(`spell1Id`/`spell2Id`), 시작/핵심/전체 아이템(`startingItemIdList`/`top1ThreeCoreIdList`/`coreItemIdList`/`shoesId`), 스킬 순서(`skillMasterList`/`skillLv15List`)까지 전부 파싱해서 씀(`parseChampionBuild`, `getChampionBuild`). 이 과정에서 기존 `extractNumberField` 파서의 버그도 하나 발견해 고쳤음: `championId`/`laneId`류 필드는 순수 숫자로 박혀있지만 `runeTotalWinrate`/`startingWinrate`/`top1ThreeCoreWinrate`/`skillMasterWinrate` 같은 **승률 필드는 `"52.72"`처럼 따옴표로 감싼 문자열**이라 기존 정규식(순수 숫자만 매치)이 이 필드들만 조용히 `null`로 반환하고 있었음 — 정규식에 선택적 따옴표(`"?`)를 추가해서 두 형태를 모두 매치하도록 수정, 실제 저장해둔 나서스(챔피언ID 75) 페이지 HTML로 수정 전/후 값을 직접 대조해서 확인함(카운터 쪽 필드는 이미 순수 숫자라 회귀 없음도 같은 방식으로 확인) |

**공통 파싱 로직**(`src/lib/scrape.ts`)은 정확한 JSON 경로를 하드코딩하지 않고, 챔피언 식별 필드(평평한 `championId`류, 또는 op.gg처럼 `champion: {key: "..."}`형태로 중첩된 슬러그) + `winRate`/`wins`류 필드를 동시에 가진 객체가 2개 이상 들어있는 배열을 페이지의 내장 데이터에서 찾는 방식이라 필드명이 조금 달라도, 배열에 마커 값이 섞여 있어도 버틸 여지가 있지만, 근본적으로는 여전히 추정입니다. 중첩 슬러그는 각 소스가 URL을 만들 때 쓰는 것과 동일한 슬러그 변환 함수로 Data Dragon 챔피언 목록을 돌려서 역매핑합니다(`genericSource.ts`의 `buildSlugResolver`).

**로컬에서 실행해보고 안 되면** 에러 메시지를 그대로 알려주세요. API 응답에는 소스별로 어떤 이유로 실패했는지(HTTP 상태 코드 / 못 찾은 부분)가 다 담겨 있어서 바로 원인을 좁힐 수 있습니다. 일부만 실패하는 경우 화면의 "N개 소스 중 M개 성공" 항목을 펼치면 소스별 에러가 보입니다. 카운터 페이지 하나의 실제 URL과 (가능하면) 그 페이지 소스를 공유해주시면 가장 빠르게 고칠 수 있습니다.

**화면에는 에러 메시지를 띄우지 않습니다.** 처음에는 6개 소스가 전부 실패하면 원인 파악을 위해 URL/HTTP 상태 코드가 그대로 담긴 빨간 배너를 화면에 띄웠는데, 실사용 단계에서는 그게 사용자에게 그냥 깨진 화면처럼 보인다는 피드백을 받아서 걷어냈습니다. 지금은 어떤 조회든 전부 실패하면(예: `/api/counters`가 502를 반환) 그 결과 영역이 그냥 비어있는 채로 남고(헤더까지 포함해서 아예 안 뜸), 원본 에러는 `console.error`로만 남습니다 — 위 문단처럼 에러 메시지가 필요하면 브라우저 개발자 도구 Console 탭을 확인해주세요. 픽 추천의 "실측 데이터 기반 전체 시너지"처럼 이미 채워진 항목 옆에 표시되는 매치업 실패도 원본 에러 대신 항상 "이 매치업 데이터를 찾지 못했습니다" 같은 고정 문구만 보여줍니다. 반면 **일부만 실패하는 경우의 "N개 소스 중 M개 성공" 펼침 목록은 그대로 유지**됩니다 — 이건 알람이 아니라 접어둔 상세 정보라 화면을 어지럽히지 않으면서도 디버깅에 필요하면 펼쳐볼 수 있기 때문입니다.

## 모바일 UI

이 앱은 브라우저 탭이 아니라 **모바일 홈 화면에 앱처럼 추가해서 쓰는 걸** 기준으로 UI를 맞췄습니다.

- **뷰포트 자동 대응**: `layout.tsx`의 `viewport` export에 `width: "device-width"`, `initialScale: 1`, `maximumScale: 1`, `userScalable: false`, `viewportFit: "cover"`를 설정해뒀습니다. 어떤 화면 비율의 기기에서 열어도 그 폭에 맞춰 렌더링되고(줌 없이), 노치/펀치홀이 있는 기기에서도 `env(safe-area-inset-*)`로 상하좌우 안전 영역만큼 `.page` 패딩을 더 줍니다.
- **더블탭 확대 · 텍스트 선택 비활성화**: `body`에 `touch-action: manipulation`(더블탭 확대 제스처 자체를 브라우저가 인식하지 않게 함) + `user-select: none` / `-webkit-touch-callout: none`(길게 눌러도 선택 팝업이나 텍스트 선택이 뜨지 않음)을 적용해 네이티브 앱에 가까운 느낌으로 만들었습니다. 단, 검색창 등 `input`/`textarea`는 예외로 `user-select: text`를 다시 켜뒀습니다 — 입력한 값은 정상적으로 선택/복사할 수 있어야 하기 때문입니다.
- **상단 탭 고정(sticky) + 가로 스크롤**: 모드 탭(라인 카운터/바텀 듀오/픽 추천/빌드)과 포지션 탭은 좁은 화면에서 줄바꿈되어 지저분해지는 대신 한 줄로 유지하고 가로로 스크롤하도록 바꿨고, 모드 탭은 스크롤해도 화면 위에 붙어있습니다(`position: sticky`).
  - 이 과정에서 CSS 함정을 하나 발견해서 고쳤습니다: `html`/`body`에 가로 스크롤 방지용으로 `overflow-x: hidden`을 걸어두면, `overflow-y`가 명시돼 있지 않을 때 브라우저가 자동으로 `overflow-y: auto`로 승격시키는 스펙 규칙 때문에 `html`과 `body`가 각각 독립된 스크롤 컨테이너가 되어버립니다. 그러면 `position: sticky` 요소가 자신이 붙어야 할 스크롤 컨테이너를 잘못 찾게 되어 고정되지 않고 그냥 스크롤을 따라 지나가 버립니다. `overflow-x: hidden` 대신 `overflow-x: clip`으로 바꿔서 이 부작용 없이 가로 스크롤만 막도록 고쳤습니다(Playwright로 `getBoundingClientRect()`를 직접 찍어서 고치기 전/후 차이를 확인했습니다).
- **PWA 홈 화면 메타**: `layout.tsx`의 `appleWebApp`(`capable`, `title: "GGOBIS"`, `statusBarStyle`)로 iOS에서 홈 화면에 추가했을 때 브라우저 주소창 없이 앱처럼 열리고 이름이 "GGOBIS"로 나오게 해뒀습니다.
- **사이트 아이콘**: 기본 Next.js `favicon.ico`(레거시 폴백으로 그대로 둠) 대신, App Router의 `icon.tsx`/`apple-icon.tsx` 컨벤션(`next/og`의 `ImageResponse`로 빌드 시 렌더링)으로 브라우저 탭 아이콘(32×32)과 iOS 홈 화면 아이콘(180×180)을 직접 생성했습니다 — 배경은 `globals.css`의 `--background`(`#0b0d11`), 글자는 `--accent`(`#5b9bff`)로 앱 배색과 맞췄고, 위에 큰 글자로 "GG" + 아래에 작은 글자로 "obis"를 2줄로 넣어서 "GGOBIS"라는 사이트 이름이 읽히게 했습니다. 애플 아이콘 쪽은 iOS가 자체적으로 모서리를 둥글게 마스킹하므로 여기서는 둥근 모서리를 넣지 않고 꽉 채운 정사각형으로 만들었습니다.
- **챔피언·포지션 선택 스크롤 최소화**: 두 가지를 함께 고쳤습니다.
  1. *슬롯을 누르면 챔피언 픽커로 자동 스크롤*: 모바일에서 위쪽의 슬롯(라인 카운터/빌드의 기준 챔피언 칸, 픽 추천의 10칸 챔피언 선택 화면)을 눌러도 화면엔 아무 변화가 없어 보이는 문제가 있었습니다 — 실제로는 활성 슬롯이 바뀌어 있지만, 픽커(`ChampionPicker`) 자체가 화면 밖 한참 아래에 있어서 사용자가 매번 손으로 스크롤해서 찾아야 했습니다. 슬롯을 실제로 누르는 액션(빈 슬롯 선택, 채워진 슬롯을 눌러 비우고 재선택)에서만 픽커를 부드럽게 스크롤해 화면에 띄우도록 `activateSlot`(`src/app/page.tsx`)을 추가했습니다 — 다음 빈 슬롯으로 자동 이동하거나(픽 하나 고르고 나면 스크롤 위치는 그대로 유지, 챔피언 하나씩 연달아 고를 때 매번 다시 스크롤할 필요 없음) 모드 탭을 바꿀 때는 일부러 스크롤하지 않습니다(사용자가 방금 위쪽 탭을 눌렀는데 갑자기 화면이 아래로 튀는 게 더 어색하다고 판단).
  2. *픽커 위치를 결과 섹션보다 앞으로 이동*: 위 스크롤 기능을 넣기 전부터, `<ChampionPicker>` 섹션 자체가 항상 페이지 맨 마지막(모든 결과 섹션보다도 뒤)에 렌더링되고 있었습니다 — 그래서 픽을 하나씩 채울수록 결과 섹션이 길어지고, 결과가 길어질수록 슬롯 바로 아래에 있어야 할 픽커가 점점 더 멀리 밀려나는 구조였습니다. 픽커를 슬롯 바 바로 아래(결과 섹션보다 앞)로 옮겨서, 결과가 아무리 길어져도 픽커까지의 스크롤 거리가 항상 일정하게 짧도록 고쳤습니다. 이 두 가지가 합쳐져서 슬롯을 누르는 순간 픽커가 항상 화면에 바로 들어옵니다(390px 너비 기준 Playwright로 검증).
- **설명/세부 지표는 기본 접힘, "OO 보기"로 펼침**: 결과 화면이 길어질수록 스크롤이 힘들어지는 문제를 줄이려고, 핵심 정보(챔피언 이름/아이콘/실제 승률/주요 배지)는 항상 보이게 두고 그 외 설명 문단과 세부 지표는 기본적으로 접어뒀습니다 — 소스별 상세(`SourceBreakdown`), 라인전 세부지표(`LaningStatsRow`), 각 섹션 도입부의 긴 설명 문단, "챔피언 특성 기반 조합 분석"/"조합 컨셉" 카드 전체, 팀 파워 커브의 라이너별 상세, 빌드 카드의 서브 룬/스펠/시작 아이템/전체 빌드 순서/스킬 순서 등입니다. 별도 React 상태 없이 네이티브 `<details>`/`<summary>`로 구현한 공용 `Details` 컴포넌트(`src/components/Details.tsx`)를 씁니다 — 모바일에서 추가 JS 핸들러 없이 안정적으로 동작하고, 열림/닫힘에 따라 "OO 보기"/"OO 숨기기" 라벨이 순수 CSS(`[open]` 속성 선택자)로 바뀝니다(`globals.css`의 `.details-toggle`). 이미 있던 "N개 소스 중 M개 성공" 펼침 목록(`SourceStatusNote`)이나 "내 챔피언 풀" 편집기처럼 원래도 접혀 있던 UI는 그대로 뒀습니다.
- **픽 추천의 10슬롯을 화면 상단에 고정**: 우리팀 5칸+상대팀 5칸 선택 현황(`.champ-select-teams`)을 결과 섹션·챔피언 픽커보다 앞이 아니라 아예 페이지 최상위로 옮기고 `position: sticky`를 걸어서, 챔피언 그리드를 스크롤하거나 결과를 한참 내려서 보는 중에도 항상 화면에 보이게 했습니다(모드 탭 `.mode-tabs` 바로 아래에 겹치지 않게 붙음). 원래는 카드(`.selected-bar`, 스플래시 아트 미리보기+새로고침 버튼 포함) 안에 있어서, 그 카드 높이만큼만 붙어있다가 카드가 다 스크롤되면 같이 사라져 버려 실질적으로 별 도움이 안 됐습니다 — 스플래시 아트 미리보기와 새로고침 버튼은 원래 자리(`.selected-bar`)에 그대로 남겨두고 고정하지 않았습니다(화면을 너무 많이 차지하면 오히려 챔피언 그리드 볼 공간이 줄어들기 때문). 390px 뷰포트에서 1,500px 스크롤 후에도 슬롯이 겹침 없이 정확히 붙어있는 것과, 스크롤된 상태에서 슬롯을 눌러도 픽커로 자동 스크롤(`activateSlot`)이 정상 동작하는 것을 Playwright로 확인했습니다.
- **선택 표시 강화**: 두 가지 모두 기존엔 얇은 파란 테두리 + 옅은 그림자뿐이라 어두운 배경에서 눈에 잘 안 띄었습니다. (1) 픽창에서 지금 채우고 있는 슬롯(`.champ-select-slot--active`)에 은은한 파란 배경 채움을 추가하고 테두리 그림자를 진하게 올렸습니다. (2) 챔피언 픽커 그리드에서 이미 보드에 놓인 챔피언 타일(`.champion-tile--selected`)에도 같은 배경 채움을 추가하고, 오른쪽 위에 작은 체크마크(✓) 배지를 붙였습니다. 이 과정에서 실제 버그도 하나 발견해 같이 고쳤습니다: 타일의 "선택됨" 표시가 원래는 **지금 활성화된 슬롯 하나의 챔피언**만 봤는데, 챔피언을 고르면 `assignActiveSlot`이 바로 다음 빈 슬롯으로 활성 슬롯을 넘겨버려서(그 슬롯은 아직 비어있음) 사실상 거의 항상 아무 타일도 "선택됨"으로 안 보이고 있었습니다 — 활성 슬롯 하나가 아니라 **보드에 채워진 모든 슬롯**의 챔피언을 선택 표시 대상으로 바꿔서, 이미 고른 챔피언들이 그리드를 스크롤하는 동안에도 계속 표시되게 고쳤습니다.
- **픽 추천의 챔피언 픽커를 평소엔 숨기고, 슬롯을 누르면 전체화면으로 띄움**: 픽 추천 모드에서는 챔피언 그리드(`ChampionPicker`)가 평소엔 아예 렌더링되지 않다가, 10슬롯 보드에서 슬롯을 하나 누르면(빈 슬롯 선택이든, 채워진 슬롯을 다시 눌러 비우고 재선택이든) 화면 전체를 덮는 오버레이(`.champion-picker-overlay`, `position: fixed; inset: 0`)로 나타나고, 상단에 "우리팀 미드 선택"처럼 지금 채우는 슬롯 이름을 보여줍니다. 챔피언을 고르면(`assignActiveSlot`) 자동으로 닫히고, 오른쪽 위 ✕ 버튼으로도 고르지 않고 닫을 수 있습니다. 열려있는 동안은 `document.body`에 `overflow: hidden`을 걸어서 그리드를 스크롤할 때 뒤에 깔린 페이지가 같이 스크롤되지 않게 했습니다. 원래는(바로 위 두 항목 참고) 픽커가 항상 페이지 어딘가에 인라인으로 떠 있어서, 슬롯을 누르면 그쪽으로 스크롤해 이동하는 방식이었는데 — 10슬롯 보드 + 결과 섹션이 이미 화면을 꽉 채우다 보니 "스크롤해서 찾아가는 것" 자체가 여전히 번거롭다는 피드백을 반영해, 아예 화면 전체를 픽커 전용 화면으로 바꾸는 방식으로 교체했습니다. (당시엔) 라인 카운터/빌드 모드는 채울 슬롯이 하나뿐이라 기존처럼 인라인 픽커 + 자동 스크롤(`activateSlot`의 `scrollIntoView`) 방식을 그대로 유지했습니다 — **이후 아래 항목에서 라인 카운터/빌드도 같은 오버레이 방식으로 통일했습니다.** Playwright로 (1) 픽 추천 진입 직후 픽커가 DOM에 없는 것, (2) 슬롯을 누르면 전체화면(뷰포트 크기와 동일한 바운딩 박스) 오버레이가 올바른 슬롯 이름과 함께 뜨는 것, (3) 챔피언 검색+선택 후 오버레이가 닫히고 실제 조회 결과에 반영되는 것, (4) ✕ 버튼으로도 닫히는 것, (5) 오버레이가 열려있는 동안 `body.style.overflow`가 `hidden`이었다가 닫으면 원래대로 돌아오는 것을 모두 확인했습니다.
- **라인 카운터/빌드도 챔피언 픽커를 전체화면 오버레이로 통일**: 바로 위 항목에서 픽 추천만 전체화면 오버레이 방식으로 바꾸고 라인 카운터/빌드는 인라인 픽커 + 자동 스크롤 방식을 그대로 남겨뒀었는데, 같은 페이지 안에서 탭마다 챔피언을 고르는 조작 방식이 서로 다르면 헷갈린다는 피드백을 받아 세 모드 모두 동일하게 오버레이 방식을 쓰도록 통일했습니다. `activateSlot`/`assignActiveSlot`/렌더링 분기에 남아있던 `mode === "advice"` 조건을 전부 없애서 이제 어느 모드에서든 슬롯을 누르면 같은 전체화면 오버레이가 뜨고, 챔피언을 고르거나 ✕를 누르면 닫힙니다. 라인 카운터/빌드는 슬롯이 하나뿐이라 오버레이 안에서 챔피언을 고르면 곧바로 결과가 조회됩니다. 더 이상 쓰이지 않게 된 인라인 픽커 섹션(`.picker-section`, `pickerSectionRef`와 그 `scrollIntoView` 로직)은 코드/CSS에서 함께 제거했습니다. Playwright로 라인 카운터/빌드/픽 추천 세 모드 모두에서 슬롯을 누르면 전체화면 오버레이(뷰포트와 동일한 바운딩 박스)가 올바른 슬롯 이름("기준 챔피언 선택" / "우리팀 미드 선택" 등)과 함께 뜨고, 챔피언을 고르거나 ✕를 누르면 닫히는 것을 확인했습니다.
- **가시성(색 대비) 강화**: 초기 배색은 배경/카드/테두리 색이 서로 너무 가까워서(`--background`/`--surface`/`--border`가 다 비슷한 톤의 어두운 회색) 카드 경계나 비활성 탭이 잘 안 보였습니다. `--border`를 눈에 띄게 밝혀 카드/탭/아이콘 테두리가 실제로 구분되게 하고, 비활성 탭도 `--surface-alt` 배경 + `--foreground` 글자색으로 바꿔 활성 탭만 도드라지던 것에서 모든 탭이 스캔 가능하게 했습니다. 결과 카드(`.results`)에는 옅은 그림자를 줘서 배경과 확실히 분리되게 했고, `<h3>` 섹션 제목은 회색(`--muted`)이 아니라 굵은 글자 + 파란 왼쪽 테두리로 바꿔 "이게 새 섹션이다"가 한눈에 보이게 했습니다. 승률 바 트랙, 챔피언 아이콘, 티어 배지, 소스 배지도 테두리/글자 굵기/배경 불투명도를 올려서 작은 글씨들이 흐릿하게 뭉개져 보이던 문제를 줄였습니다.
- **픽 추천 추천 개수(5/10/15) 선택**: 픽 추천 결과 화면 상단(내 챔피언 풀 편집기 바로 아래)에 "추천 개수" 탭(5개/10개/15개, 기본 5개)을 추가했습니다 — 고르면 `/api/pickadvice`에 `count` 쿼리 파라미터로 넘어가고, 서버가 "라인전 유리한 픽"/"시너지 좋은 픽"/"라인전 + 시너지 둘 다 좋은 픽" 세 목록 모두 그 개수만큼만 잘라서 응답합니다(`src/app/api/pickadvice/route.ts`의 `RECOMMEND_COUNT_OPTIONS`/`parseRecommendCount`). "둘 다 좋은 픽"은 원래 상위 5개로 고정돼 있던 걸 이 값을 쓰도록 바꿨습니다. 다만 파워 커브/빌드/라인전 세부지표 같은 부가 정보는 지금까지처럼 상위 5개 후보에만 붙습니다(`POWER_CURVE_CANDIDATE_LIMIT` 등, 요청마다 사이트에서 개별 조회해야 해서 전체 목록에 다 붙이면 느려짐) — 10개/15개를 고르면 6번째 이후 픽들은 승률/티어만 나오고 세부 배지·"세부정보 보기"는 비어 있을 수 있습니다. 실제 스크래핑 사이트 접근이 막힌 이 개발 환경에서는 라인전/시너지 데이터 자체를 못 받아와 목록이 비어 있어서(사이트 차단은 알려진 제약사항 — 위 참고), `/api/pickadvice`를 Playwright의 `page.route`로 가로채서 5/10/15개짜리 가짜 응답을 흘려보내는 방식으로 "선택한 개수만큼 정확히 렌더링되는지"를 검증했습니다.
- **챔피언 풀 적용/미적용 토글**: "내 챔피언 풀" 편집기에 챔피언을 1명 이상 등록하면 체크박스(`.pool-apply-toggle`, 기본 켬)가 나타나서, 풀 자체는 그대로 둔 채 지금 조회에 적용할지만 껐다 켰다 할 수 있습니다 — 예전엔 풀을 잠깐 무시하고 전체 챔피언 대상 추천을 보려면 등록된 챔피언을 다 지웠다가 나중에 다시 등록해야 했습니다. 껐을 때는 `runLookup`이 `tier1`/`tier2`/`tier3` 쿼리 파라미터 자체를 보내지 않아서(풀은 `localStorage`에 그대로 남아있음) 서버 입장에서는 풀이 아예 없는 것과 동일하게 동작하고, 편집기 요약 텍스트도 "N명 설정됨 (미적용)"으로 바뀝니다. Playwright로 체크박스를 껐을 때 실제 API 요청에 `tier1`이 빠지는 것과, 다시 켰을 때 돌아오는 것을 확인했습니다. **위치 수정**: 처음엔 이 체크박스를 "내 챔피언 풀" `<details>` 패널 안(펼쳐야 보이는 위치)에 뒀었는데, 그러면 패널이 기본값대로 접혀있을 땐 체크박스도 같이 숨어서 굳이 펼쳐야만 껐다 켤 수 있었습니다. 체크박스를 `<details>` 바깥, 항상 보이는 위치로 옮겨서 패널을 펼치지 않고도(접힌 채로도) 바로 켜고 끌 수 있게 고쳤습니다 — `ChampionPoolEditor`를 감싸는 `<div className="champion-pool-editor">`(카드 배경/테두리 스타일은 이쪽으로 옮김) 안에서 체크박스를 `<details>`보다 앞에 형제로 배치. Playwright로 패널을 접은 상태에서도 체크박스가 보이고 실제로 클릭해서 토글되는 것을 확인했습니다.
- **CC 표시에서 하드 CC와 일반 CC 색 구분**: 픽 추천 10슬롯 보드의 CC 점(`.champ-select-cc-dot`)이 기존엔 "하드 CC 있음(빨강)"/"없음(투명)"/"확인 중(회색 점선)" 세 상태뿐이었는데, "CC가 있긴 한데 둔화 정도인지 완전 무력화인지" 구분이 안 됐습니다. `src/lib/championSkills.ts`가 이미 계산해두고 있던 "slow" 태그(둔화 키워드 매칭)를 `hasSoftCC`로 새로 노출시켜서, 하드 CC(기절/속박/공포/도발/침묵/수면/제압/공중으로 띄우기 등 완전히 무력화하는 효과)는 기존처럼 빨강(`--bad`)으로, 하드 CC는 없고 둔화 같은 일반 CC만 있으면 새로 추가한 호박색(`--warn`, `#f5b942`)으로, 아예 없으면 기존처럼 빈 점으로 구분됩니다(`ccDotState` 함수, `src/app/page.tsx`). 팀 합계("CC 보유 챔피언 — N명")는 지금까지처럼 하드 CC 기준만 셉니다 — 일반 CC는 실제 전투 영향력이 하드 CC와 크게 달라서 같은 합계에 섞으면 오히려 오해를 줄 수 있다고 판단했습니다. 이 데이터도 Data Dragon 챔피언 상세 조회가 필요해 이 환경에서는 실제로 못 받아왔고, `/api/pickadvice` 응답을 가짜로 흘려보내 하드/일반/없음 세 조합을 동시에 렌더링해서 점 색·타이틀 텍스트가 각각 맞게 나오는 것을 Playwright로 확인했습니다.
- **챔피언 풀을 포지션별로 분리**: 예전엔 "내 챔피언 풀"이 티어(1~3)로만 나뉘어 있고 포지션 구분이 없어서, 미드에서 등록한 챔피언이 탑 추천에도 똑같이 섞여 나왔습니다(럭스를 등록해두면 탑 추천에도 럭스가 뜨는 식). `ChampionPool` 타입을 `Record<1|2|3, number[]>`(티어만) → `Record<Position, Record<1|2|3, number[]>>`(포지션별로 티어 버킷을 따로)로 바꿔서, 지금 픽 추천에서 보고 있는 포지션 탭(`position` 상태 — 이미 "내 포지션" 선택에 쓰이던 바로 그 탭)의 풀만 등록/조회/적용되게 했습니다. 새 UI 서페이스를 따로 만들지 않고 기존 포지션 탭을 그대로 재사용한 것 — 탑 탭에서 "내 챔피언 풀"을 펼쳐 챔피언을 등록하면 탑 풀에, 미드 탭으로 바꾸면 미드 풀을 보고 편집하게 됩니다. 서버(`/api/pickadvice`)로 보내는 `tier1`/`tier2`/`tier3` 파라미터도 현재 포지션의 버킷만 담아서 보내므로 서버 쪽 코드는 변경 없음(원래도 그냥 "받은 챔피언 ID들로만 제한"이었지, 포지션 개념을 몰랐음). `localStorage` 저장 형식도 포지션별 중첩 구조로 바뀌었는데, 예전 형식(포지션 키 없이 티어만 있는 평평한 객체)으로 저장된 데이터를 읽을 때는 `isValidTierBucket`으로 각 포지션 키를 검증해서 못 찾으면 그냥 빈 풀로 시작하도록 했습니다(깨지거나 잘못 해석하는 대신 조용히 한 번 초기화됨 — 마이그레이션이 필요할 만큼 데이터가 크지 않은 개인용 로컬 설정이라 이 정도로 충분하다고 판단). Playwright로 (1) 탑 탭에서 등록한 챔피언이 정글 탭엔 안 보이는 것, (2) 탑으로 다시 돌아오면 그대로 남아있는 것, (3) 실제 `/api/pickadvice` 요청에 현재 포지션의 `tier1`만 실리는 것(다른 포지션 탭에선 안 실림), (4) 두 포지션에 각각 등록한 뒤 새로고침해도 `localStorage`에서 각자의 풀을 정확히 복원하는 것을 확인했습니다.
- **상대 라이너를 몰라도 조합 기반으로 픽 추천**: "내 픽 추천"(라인전 유리한 픽)은 op.gg/u.gg 등의 카운터 페이지가 특정 상대 챔피언을 기준으로만 존재하는 데이터라서, 상대 라이너(내 맞상대)를 안 채우면 실제 승률 자체가 없어 지금까지는 이 섹션이 통째로 안 떴습니다 — 상대팀/우리팀에 다른 챔피언을 아무리 채워도 정작 "누굴 픽할지" 추천은 못 받는 상태였습니다. 상대 라이너가 없을 때는 `compFitPicks`라는 대체 추천을 새로 계산합니다(`computeCompFitPicks`, `src/app/api/pickadvice/route.ts`) — 실제 승률 데이터 없이, 이미 채운 상대팀 조합에 대한 태그 기반 적합도(`scoreEnemyCompFit`, 원래도 "라인전 유리한 픽" 순위에 소폭 반영하던 바로 그 신호)와 이미 채운 우리팀에 대한 실측 아군 시너지(`allySynergy`, 마찬가지로 기존 계산 재사용 — 새로 조회하지 않음)만으로 순위를 매깁니다. **의도적으로 "내 챔피언 풀"에 등록된 챔피언으로만 후보를 제한**합니다 — Data Dragon의 챔피언 태그(전사/마법사/서포터 등)는 역할군이지 라인 배정이 아니라서, 풀 없이 전체 로스터를 대상으로 하면 이 포지션에 아무도 안 하는 챔피언까지 섞여 나올 위험이 큽니다(현재 픽 추천이 포지션별 챔피언 풀을 갖춘 직후라 타이밍도 잘 맞았습니다 — 바로 위 항목 참고). 그래서 이 포지션에 풀이 등록되어 있지 않으면 서버가 `null`을 주고, 프론트엔드는 "내 챔피언 풀"에 등록하면 추천받을 수 있다는 안내만 보여줍니다(등록 UI로 바로 유도). 실제 승률/게임 수는 전혀 없으므로 `WinRateBar`는 안 쓰고 적합도 배지(`CompFitBadge`)와 아군 시너지 배지(`AllySynergyBadge`)만 보여줘서, 이게 실측 승률이 아니라 조합 기반 추정이라는 걸 시각적으로도 구분되게 했습니다. 상대 라이너를 채우는 순간 원래의 실제 승률 기반 "라인전 유리한 픽"으로 자연스럽게 넘어갑니다. 이 환경은 실제 스크래핑 사이트 접근이 막혀 있어서, `/api/pickadvice` 응답을 Playwright로 가로채 (1) 풀이 있고 상대팀 일부만 채운 경우 조합 기반 추천 목록이 뜨고 그 안에 승률 바가 하나도 없는 것, (2) 이 포지션에 풀이 없는 경우 안내 문구만 뜨는 것을 확인했습니다.
- **챔피언 풀 편집 중 다른 티어에 이미 있는 챔피언 표시**: 한 포지션의 풀은 1~3티어로 나뉘어 있는데, 예를 들어 2티어를 편집하다가 이미 1티어에 등록해둔 챔피언을 못 보고 또 고르는 실수가 있을 수 있었습니다(실제로는 `toggleChampionInPool`이 한 챔피언을 항상 최대 한 티어에만 두도록 자동으로 옮겨주긴 하지만, 편집 중엔 "얘가 이미 다른 티어에 있다"는 게 안 보였습니다). `ChampionPicker` 공용 컴포넌트에 `elsewhereLabels`라는 선택적 prop을 추가해서(championId → "N티어" 같은 짧은 라벨), 지금 편집 중인 티어가 아니라 같은 포지션의 다른 티어에 있는 챔피언 타일에 호박색(`--warn`) 테두리와 "N티어" 배지를 붙였습니다 — 기존 "선택됨"(파란 테두리+체크) 표시와는 확실히 다른 색이라 헷갈리지 않습니다. 배지가 붙어도 클릭은 그대로 막지 않았습니다 — 눌러서 이 티어로 옮기는 것 자체는 유효한 동작(예: 이 챔피언을 1티어에서 2티어로 재분류)이라, 안내만 하고 막지는 않는 쪽을 택했습니다(타일에 마우스를 올리면 "이미 1티어에 있음 — 선택하면 여기로 이동"이라는 툴팁도 뜸). 이 prop은 챔피언 풀 편집기에서만 넘기고 다른 곳(픽 추천의 전체화면 챔피언 오버레이 등)에서는 안 넘기므로 그쪽 동작은 전혀 안 바뀝니다. Playwright로 챔피언을 1티어에 등록한 뒤 2티어 편집 화면을 열어서 배지가 뜨는 것, "선택됨" 표시와 동시에 뜨지 않는 것, 클릭하면 실제로 1티어에서 빠지고 2티어로 옮겨가는 것을 확인했습니다.
- **픽 추천 10슬롯 중 "내 픽" 슬롯도 채워서 조합을 볼 수 있게 함**: 예전엔 지금 보고 있는 포지션 탭에 해당하는 우리팀 슬롯("내 픽")이 항상 잠겨있어서("추천 대상 자리", 채울 수 없는 정적 표시) 정작 내가 그 자리에 뭘 넣었을 때 팀 조합이 어떻게 보이는지 확인할 방법이 없었습니다. `Slot`에서 `disabled` 개념 자체를 없애서 이제 10슬롯 전부(우리팀 5 + 상대팀 5) 다른 슬롯과 완전히 동일하게 채울 수 있고, 지금 포지션에 해당하는 슬롯에는 파란 "내 픽" 배지만 붙여서 어느 슬롯인지 표시합니다(`champ-select-slot--mine`/`champ-select-mine-badge`). 채워 넣으면 서버 쪽 코드 변경 없이 그대로 팀 조합 분석(`compHeuristic`)·조합 컨셉(`compConcepts`)·CC 정보·팀 파워 커브·실측 시너지 계산에 반영됩니다 — 애초에 서버는 "우리팀 각 포지션에 채워진 챔피언"을 그냥 그대로 다 읽어서 쓰고 있었고, 이 슬롯만 클라이언트에서 항상 비워둔 채였을 뿐이라 서버는 손댈 필요가 없었습니다. **포지션 탭을 바꿔도 슬롯 값은 그대로 유지**됩니다 — 예전엔 탭을 바꾸면 새로 "내 픽"이 된 슬롯을 강제로 비웠는데, 이제는 모든 슬롯이 동등하게 취급되니 그럴 이유가 없어졌습니다(`changePosition`이 이제 어떤 슬롯도 건드리지 않고 활성 슬롯/조회 결과만 갱신). 픽 추천 목록(라인전 유리한 픽 등)은 여전히 상대 라이너 슬롯을 기준으로 계산되므로 "내 픽"을 채웠다고 추천이 사라지지는 않습니다 — 조합 미리보기와 추천을 동시에 쓸 수 있습니다. Playwright로 탑 탭에서 "내 픽" 배지가 뜨는 것, 클릭하면 전체화면 오버레이가 열려 채울 수 있는 것, 정글 탭으로 바꾸면 배지가 정글 슬롯으로 옮겨가면서도 탑 슬롯에 채워둔 챔피언은 그대로 남아있는 것을 확인했습니다.
- **픽 추천 순위: 실제 승률 차이가 ±1.5%p 이내일 때만 챔피언 풀 티어로 정렬**: 챔피언 풀이 적용된 상태에서, 예전엔 등록해둔 티어가 실제 승률 차이보다 항상 우선했습니다 — 1티어로 등록한 챔피언의 실제 승률이 44%든 뭐든, 3티어 챔피언의 실제 승률이 아무리 높아도(예: 60%) 무조건 1티어가 먼저 나왔습니다. 이제는 그 반대로 바뀌었습니다: 인접한 두 후보의 실제 승률 차이가 1.5%p 이하일 때만 챔피언 풀 티어가 순서를 정하고, 그보다 크게 벌어지면 실제 승률이 그대로 이깁니다(`applyTierTiebreak`, `TIER_TIE_THRESHOLD`, `src/app/api/pickadvice/route.ts`) — "실제 데이터가 우선, 티어 선호도는 진짜 우열을 가리기 힘들 때만 참고"라는 이 앱의 원래 원칙에 맞춘 것입니다. 구현은 단순한 "두 후보가 가까우면 티어로, 아니면 승률로" 비교 함수 하나로 만들지 않고(그런 방식은 A-B가 가깝고 B-C가 가까워도 A-C는 먼 경우에 비교가 일관되지 않아 `Array.prototype.sort`가 결과를 보장 못 함 — 이행성이 깨진 비교자 문제), 먼저 "인접한 승률 차이가 1.5%p 이하로 쭉 이어지는 구간"을 통째로 찾아 묶은 다음, 그 구간 안에서만 티어로 다시 정렬하는 방식(`applyTierTiebreak`)을 썼습니다 — 구간 밖 순서는 전혀 안 건드립니다. 티어 기반 재정렬이 일어나던 4곳(`restrictToPool`, `refineTopWithSkillFit`, `refineTopWithPowerCurveAndLaning`, `applyBuildFitBonus`) 전부 이 함수로 통일해서, 파워 커브/빌드 적합도 같은 나중 단계가 앞 단계의 완화된 순서를 다시 "티어 절대 우선"으로 덮어써버리는 일이 없게 했습니다. `Math.abs(a - b) <= 0.015`가 부동소수점 오차로 정확히 경계값(예: 0.530 - 0.515 = 0.015000000000000013)을 근소하게 벗어나 "안 가까움"으로 잘못 판정하는 걸 막기 위해 아주 작은 여유값(1e-9)도 더했습니다. 이 클러스터링 로직 자체는 순수 함수라 실제 스크래핑 데이터 없이도 Node로 직접 8가지 케이스(큰 격차/작은 격차/경계값/체인 클러스터링/섞인 경우/풀 미적용/티어 없는 후보 등)를 단위 테스트해 전부 통과를 확인했고, `/api/pickadvice` 응답을 흘려보내는 방식으로 프론트엔드가 서버가 정렬한 순서를 그대로(재정렬 없이) 렌더링하는 것도 확인했습니다.
- **빌드 탭이 lol.ps 하나만 실패해도 통째로 안 뜨던 버그 수정**: "빌드" 탭은 lol.ps를 먼저 조회하고, 그게 성공해야만 뒤이어 DeepLoL을 조회해서 두 카드를 나란히 보여주는 구조였습니다 — lol.ps 요청이 실패하면(사이트 구조 변경, 일시적 차단/레이트리밋 등) 즉시 예외를 던지고 그 뒤에 있던 DeepLoL 요청은 아예 시도되지도 않아서, DeepLoL은 멀쩡히 응답 가능한 상태여도 빌드 탭 전체가 그냥 빈 화면으로 남았습니다(에러 메시지도 없이 조용히 실패). lol.ps와 DeepLoL 요청을 `Promise.allSettled`로 동시에 시작해서 서로 독립적인 best-effort로 바꿨습니다 — 이제 한쪽이 실패해도 다른 쪽 카드는 정상적으로 뜨고, 실패한 쪽 자리에는 "OO 빌드 데이터를 가져오지 못했습니다"라는 짧은 안내만 남습니다(픽 추천 API의 `annotateWithBuild`/`annotateWithDeeplolBuild`가 이미 쓰던 것과 같은 원칙). 라인 카운터 탭의 배경 빌드 조회(`counterBuild`)는 원래도 독립적인 best-effort라 이 버그가 없었습니다.
- **라인 카운터가 전부 실패하면 아무 표시도 없이 비어있던 문제 수정**: 6개 소스가 전부 실패하는 경우(`/api/counters`가 502를 응답하는 유일한 경우) 조회 자체는 실행됐는데 결과 섹션이 아예 렌더링되지 않아서, 버튼을 눌러도 화면에 아무 변화가 없는 것처럼 보였습니다. 이제 이 경우엔 "6개 소스 모두에서 카운터 데이터를 가져오지 못했습니다. 잠시 후 다시 시도해보세요."라는 안내 문구를 보여줍니다 — 라인 카운터 자체의 매치업 데이터(스크래핑 성공 여부)와 무관하게, 최소한 "조회는 됐는데 데이터가 없다"와 "아직 조회 전이다"를 구분할 수 있게 했습니다. 두 항목 모두 이 환경에서 실제 외부 사이트 접근이 막혀있는 걸 이용해서(모든 소스가 항상 실패하는 상태), Playwright의 `page.route`로 lol.ps만 실패시키거나 6개 전부를 실패시키는 가짜 응답을 흘려보내 각 시나리오를 재현하고 고쳐진 동작을 확인했습니다. **다만 이 두 수정은 UI가 실패를 삼키던 문제를 고친 것이지, 실제 배포 환경에서 스크래핑 자체가 왜 실패하는지(사이트 구조 변경/차단 등)는 확인하지 못했습니다** — 이 환경 자체가 6개 사이트와 Data Dragon 모두에 아웃바운드 접속이 막혀 있어서 실제 스크래핑 성공 여부를 검증할 방법이 없습니다(위 "각 소스 연동 신뢰도" 표 참고).
- **핵심 태그 / 게임 스타일 표시**: 픽 추천("라인전 유리한 픽"/"시너지 좋은 픽"/"조합 기반 추천")과 라인 카운터 목록의 상위 후보 카드에 두 종류의 짧은 칩을 새로 붙였습니다 — 둘 다 "핵심 스킬/게임 승리 플랜을 반영해달라"는 요청에서 나왔지만, 데이터로 뒷받침되는 정도가 서로 달라서 색과 문구를 의도적으로 다르게 뒀습니다.
  1. **핵심 태그** (파란 칩 — 하드CC/둔화/기동성/보호막·회복/장거리): 새 데이터가 아니라, 위 "상위 5개는 실제 스킬 조합까지 봅니다"/"CC 표시" 항목에서 이미 순위 보정·CC 점 색깔에만 쓰고 있던 `championSkills.ts`의 `hasHardCC`/`hasSoftCC`/`hasMobility`/`hasShieldOrHeal`/`hasLongRange`를 처음으로 후보 카드에 직접 노출한 것입니다(`toKeyTags`, `KeyTags` 타입 — 전체 스킬 설명 텍스트가 아니라 이 다섯 불리언만 API로 내려줌). Data Dragon 공식 스킬 설명 텍스트를 한국어 키워드로 매칭해 추론한 값이라는 한계(휴리스틱, 완벽한 분류 아님)는 원래 기능과 동일합니다. 새 네트워크 요청이 추가되진 않았습니다 — 순위 보정(`refineTopWithSkillFit`)/조합 컨셉 분석이 이미 상위 후보의 Data Dragon 상세 데이터를 가져오고 있어서, 그 캐시된 결과에서 다섯 값만 꺼내 붙였습니다. 다만 순위 보정과 달리 **상대팀이 하나도 안 채워져 있어도** 붙습니다(`annotateWithKeyTagsAndConceptFits`, `refineTopWithSkillFit`과 분리된 별도 best-effort 패스) — 핵심 태그는 "이 후보가 상대에게 얼마나 잘 맞는지"가 아니라 "이 후보 자체가 뭘 갖고 있는지"라서 상대 유무와 무관하게 보여줄 수 있는 정보이기 때문입니다. 라인 카운터 탭(`/api/counters`)에는 이런 Data Dragon 상세 조회 패스가 원래 없었어서 이번에 새로 추가했습니다(`attachKeyTagsAndConceptFits`, `src/app/api/counters/route.ts`) — 상위 5개(`KEY_TAGS_CANDIDATE_LIMIT`)에만 붙는 이유는 다른 상위-N 전용 기능들과 동일(후보마다 챔피언 하나씩 별도 요청).
  2. **게임 스타일** (보라 칩 — 돌진/이니시·포킹·쌍포/보호·한타·스플릿 푸시): "게임 승리 플랜"은 실제 데이터로 증명할 수 있는 영역이 아니라서, 이미 팀 단위로 존재하던 `compConcepts.ts`의 5개 조합 컨셉 판정 로직(`fitsEngage`/`fitsPoke`/`fitsProtectCarry`/`fitsProtectPeel`/`fitsTeamfight`/`fitsSplitPush`)을 챔피언 한 명 단위로 그대로 재사용했습니다(`championConceptFit`) — 새로운 판정 기준을 만들지 않고 기존 위 "조합 컨셉" 항목과 완전히 같은 신호(태그+ability 키워드)만 씁니다. 팀 단위 `analyzeCompConcepts`의 "protect"는 캐리 역+보호 역이 팀 전체에 **둘 다** 있어야 인정하는 반면, 개인 단위에서는 둘 중 **하나만** 있어도 "protect"에 해당한다고 판정합니다(혼자서는 한쪽 역할만 할 수 있으므로) — 그 외 4개 컨셉은 팀/개인 판정 기준이 동일합니다. 라벨은 기존 조합 컨셉 카드가 쓰던 `COMP_CONCEPT_LABELS`를 그대로 재사용해 같은 챔피언이 어디서든 같은 이름으로 불립니다. **실측 승률이 아니라 이 앱이 정리한 전략적 분류라는 점**이 위 조합 컨셉 항목과 동일하게 적용되고, 칩에도 실측 데이터가 아니라는 툴팁을 달아뒀습니다. 핵심 태그와 같은 데이터 소스(같은 Data Dragon 상세 조회)에서 같이 계산되므로 별도 요청 추가 없이 함께 붙습니다.

  compFitPicks("조합 기반 추천")에는 위 두 칩을 붙이는 로직을 별도 함수로 만드는 대신 `computeCompFitPicks` 안에 인라인으로 넣었습니다 — `CompFitPickEntry`가 `PickEntry`와 달리 승률/게임 수 필드 자체가 없어서(`annotateWithKeyTagsAndConceptFits`를 그대로 재사용할 타입이 아님) 같은 조회+부착 로직만 별도로 반복했습니다. 실제 스크래핑 사이트 접근이 막힌 이 환경에서는 Data Dragon도 마찬가지로 접근할 수 없어서, `/api/counters`·`/api/pickadvice` 응답에 `keyTags`/`conceptFits`가 채워진 가짜 데이터를 Playwright `page.route`로 흘려보내 라인 카운터 목록과 픽 추천 "라인전 유리한 픽" 목록 양쪽에서 칩(예: "하드CC", "돌진/이니시")이 실제로 렌더링되는 것을 확인했습니다.
- **라인전 팁 (15분 CS·솔로킬 기반)**: 위 "라인전 세부지표"(`LaningStatsRow`)가 보여주던 lol.ps의 실측 15분 CS 차이/솔로킬 횟수를, 펼쳐야만 보이던 숫자 표에서 그치지 않고 바로 눈에 띄는 조언 문장으로도 보여줍니다(`buildLaningTips`, `LaningTipList`, `src/app/page.tsx`) — **새 스크래핑이나 서버 계산이 아니라, 이미 조회해서 화면 어딘가에 있던 실측 수치를 클라이언트에서 순수 함수로 문장화**한 것입니다(`PowerCurveBadge`의 "초반형/후반형"이나 `ccDotState`처럼, 이 앱이 이미 쓰던 "실제 숫자 → 짧은 한국어 라벨" 패턴을 그대로 따름). 두 가지 신호만 씁니다:
  - **15분 CS 차이**가 평균 10개 이상 벌어지면(`CS_LEAD_THRESHOLD`) — 앞서면 "우위를 살려 라인을 밀고 상대를 압박해보세요", 밀리면 "무리한 교전보다 안전하게 CS 챙기기에 집중하세요".
  - **15분 이전 솔로킬 횟수 차이**가 0.15 이상 벌어지면(`SOLO_KILL_LEAD_THRESHOLD`) — 우리 쪽이 많으면 "상대가 무리하게 들어올 때 각을 노려보세요", 상대 쪽이 많으면 "혼자 스킬 맞을 상황을 만들지 않도록 주의하세요".

  두 기준값 모두 `laningFitScore`의 "±2000골드 = 대략 한 등급 스윙"과 같은 성격(정밀하게 보정할 더 큰 데이터셋이 없어 보수적으로 잡은 값)이며, 어느 쪽 기준도 안 넘으면 그 신호에 대한 팁은 아예 안 뜹니다(빈 배지를 남기지 않는 기존 원칙 그대로). **라인 카운터 탭**에는 이런 lol.ps 1:1 비교 조회 자체가 원래 없었어서 이번에 새로 추가했습니다(`attachLaningStats`, `src/app/api/counters/route.ts`, 상위 5개 카운터에만 — `LANING_STATS_CANDIDATE_LIMIT`, 핵심 태그 조회와 같은 이유로 Data Dragon 조회와는 별개로 `Promise.all`로 동시에 실행). **픽 추천 탭**은 "라인전 유리한 픽"(`counterPicks`)의 상위 5개와 "실측 데이터 기반 전체 시너지"의 이미 채워진 라인 매치업들에 이미 이 lol.ps 데이터(`laningStats`)가 붙어 있어서 서버 변경 없이 바로 문장화만 추가했습니다(서포터 시너지 픽은 특정 상대 라이너가 없어 이 데이터 자체가 없으므로 팁도 뜨지 않습니다 — 기존 라인전 세부지표와 동일한 제약). 팁 문구는 배지 줄 바로 아래, 접어둔 "세부정보"/"소스별 상세"를 펼치지 않아도 항상 보이는 위치에 뜨고, 근거가 된 실제 숫자(라인 카운터 탭은 새로 붙인 라인전 세부지표, 픽 추천은 기존 라인전 세부지표)는 그 아래 접힌 상세에서 그대로 확인할 수 있습니다. 실제 lol.ps 접근이 막힌 이 환경에서는 `/api/counters`·`/api/pickadvice` 응답에 CS 우위+솔로킬 열세, CS 열세+솔로킬 우위 두 조합을 넣은 가짜 `laningStats`를 Playwright `page.route`로 흘려보내 두 탭 모두에서 해당 팁 문장이 정확히 뜨는 것을 확인했습니다.
- **파워 커브를 더 폭넓게 사용**: 파워 커브(lol.ps 분당 승률, `earlyWinRate`/`midWinRate`/`lateWinRate`)는 지금까지 (1) 픽 추천 후보 카드에 초반/후반 %로 표시, (2) 팀 전체 라인들을 평균 낸 "팀 파워 커브" 카드, (3) 팀이 가장 강한 구간(`teamPeak`)에 후보 자신의 그 구간 승률이 얼마나 맞는지를 `allySynergyFit`에 블렌딩(`POWER_CURVE_TEAM_FIT_BLEND`) — 이 세 곳에만 쓰이고 있었습니다. 두 가지를 새로 추가했습니다.
  1. **상대 라이너와의 직접 비교(픽 추천)**: 지금까지는 "우리팀 전체가 강한 구간에 맞는지"만 봤지, "이 후보가 정확히 이 상대와 붙었을 때 초반/후반에 유리한지"는 전혀 안 봤습니다. 이제 후보와 상대 라이너 양쪽의 파워 커브를 둘 다 가져와서(`enemyCurve`, `refineTopWithPowerCurveAndLaning`에서 한 번만 조회 — 후보마다 다시 조회하지 않음) 초반/후반 승률 차이를 평균 내 0.5 중립~1.0 스케일로 변환합니다(`powerCurveVsFitScore`, ±10%p를 대략 한 등급 스윙으로 잡음 — `laningFitScore`의 ±2000골드와 같은 성격의 보수적 값). 이 값은 CS@15 기반 `laningFitScore`와 평균 내(`combinedLaningFit`) 기존 `LANING_STATS_BLEND` 슬롯에 그대로 들어가므로, `PICK_REAL_WEIGHT`/`PICK_ENEMY_FIT_WEIGHT`/`PICK_ALLY_SYNERGY_WEIGHT` 같은 최상위 가중치를 다시 재분배할 필요가 없었습니다. 화면에는 "파워 커브상 상대보다 유리/크게 유리" 배지(`PowerCurveVsEnemyBadge`)로 뜨는데, `CompFitBadge`와 같은 원칙으로 유리할 때만 보여줍니다(불리해도 배지를 굳이 안 띄움 — "배지 없음"이 곧 "특별히 유리하지 않다"는 뜻).
  2. **라인 카운터 탭에 파워 커브 자체를 새로 연결**: `/api/counters`에는 파워 커브 조회가 아예 없었습니다. 상위 5개 카운터에 조회한 조회 챔피언 자신의 파워 커브와, 각 카운터의 파워 커브를 둘 다 가져와서(`attachPowerCurve`) 초반/후반 % 배지(기존 `PowerCurveBadge` 재사용)와 위 1번과 같은 원리의 비교 배지(`powerCurveVsMineFit`)를 붙였습니다 — "이 챔피언이 통계상 카운터이긴 해도, 파워 커브상으로는 내 쪽이 유리한 구간이 있다"는 걸 알 수 있게 됩니다. `getPowerCurve` 자체는 lol.ps가 그 챔피언의 주 라인 데이터만 주므로(다른 기능들과 같은 제약), 요청한 라인과 다르면 `powerCurveLaneNote`로 표시합니다.

  두 곳 모두 새 네트워크 요청은 후보/카운터당 파워 커브 조회 1건씩(캐시됨, `CACHE_TTL_MS`)이라 기존 파워 커브 조회 규모(상위 5개 한정)를 벗어나지 않습니다. 실제 lol.ps 접근이 막힌 이 환경에서는 `/api/pickadvice`·`/api/counters` 응답에 `earlyWinRate`/`lateWinRate`/`powerCurveVsEnemyFit`/`powerCurveVsMineFit`가 채워진 가짜 데이터를 Playwright `page.route`로 흘려보내 두 탭 모두에서 파워 커브 %와 "파워 커브상 상대보다 유리" 배지가 정확히 뜨는 것을 확인했습니다.
- **픽 추천에서 챔피언 선택을 빈 슬롯으로 두기**: 지금까지도 채워진 슬롯을 누르면 내부적으로는 바로 비워지고(`clearSlot`) 챔피언 선택 화면이 다시 열렸는데, 그 상태에서 아무것도 고르지 않고 ✕로 닫으면 실제로는 빈 슬롯으로 남아있었습니다 — 다만 이게 의도된 동작인지 사용자 입장에서 전혀 알 수 없는, 우연히 되는 부작용에 가까웠습니다. 챔피언 선택 화면 상단, ✕ 버튼 옆에 **"빈 슬롯으로 두기"** 버튼을 명시적으로 추가했습니다(`blankActiveSlot`, `src/app/page.tsx`) — 누르면 지금 채우던 슬롯을 비우고 선택 화면을 닫습니다. 이미 채워진 슬롯을 눌러 재선택하려다 마음이 바뀐 경우든, 원래 비어있던 슬롯을 열었다가 그냥 비워두기로 한 경우든 결과는 동일(null)하므로 두 경우를 구분해서 버튼을 숨기지 않고 항상 보여줍니다. 라인 카운터·빌드·픽 추천 세 모드 모두 같은 전체화면 선택 화면을 공유하므로 어디서나 동일하게 동작합니다. Playwright로 빈 슬롯을 열었을 때 버튼이 보이는 것, 채워진 슬롯을 눌러 재선택 화면을 연 뒤 이 버튼을 누르면 화면이 닫히고 그 슬롯이 실제로 비어있는 것을 확인했습니다.
- **표본(게임 수)이 적어서 승률이 우연히 튄 항목이 위로 오지 않게 함**: 처음에는 "지표 수(게임 수) 많은 순으로 보기"라는 별도 정렬 모드로 요청받았는데, 논의 끝에 "게임 수를 50/100 기준으로 구간을 나누고, 그 구간 안에서는 게임 수 자체는 더 이상 안 보고 승률로만 정렬"하는 방식으로 정리됐습니다 — 예를 들어 3게임 100% 승률 챔피언이 500게임 55% 승률 챔피언보다 위로 오는 걸 막는 게 목적입니다. 게임 수를 **100+/50~99/50 미만** 세 구간(신뢰도 순, `sampleReliabilityTier`, `src/lib/sampleSize.ts`)으로 나누고, 이 구간을 정렬의 최우선 기준으로 삼습니다(구간 안에서는 정확한 게임 수 차이는 안 보고 순수 승률로만 정렬 — "게임 수로 세분화"가 아니라 "표본 부족 필터링"이 목적이라 이 정도 해상도로 충분하다고 판단). 별도 토글 UI를 추가하는 대신, 기존 순위 로직 자체에 최우선 기준으로 얹었습니다(항상 켜져 있음) — 라인 카운터/픽 추천 모두 "믿을 만한 승률"을 보여준다는 이 앱의 기본 취지에 항상 맞아야지, 껐다 켰다 할 이유가 없다고 판단했습니다.
  - **라인 카운터 탭**(`/api/counters`): 기존의 단순 `winRate` 정렬을 "구간 먼저, 구간 안에서는 승률" 비교자로 교체했습니다.
  - **픽 추천 탭**(`/api/pickadvice`): 이미 실제 승률(65%)·상대 조합 적합도(15%)·아군 시너지(20%)를 블렌딩하는 `pickRankScore` 공통 함수가 있어서, 그 위에 신뢰도 구간을 곱셈으로 얹었습니다(`SAMPLE_RELIABILITY_WEIGHT = 10` — 블렌딩된 점수가 항상 0~1 사이라서, 10을 곱한 구간 순위가 그 어떤 블렌딩 조합보다도 항상 압도적으로 커서 구간이 100% 우선하도록 보장). 즉 "표본 구간 → (구간 안에서) 기존 블렌딩 순위" 순서로 정렬되고, 기존 순위 공식 자체는 그대로 살아있습니다. 챔피언 풀 티어 재정렬(`applyTierTiebreak`)도 표본 구간 경계를 넘어서 근접 승률을 재정렬하지 않도록 함께 고쳤습니다 — 그렇지 않으면 표본이 적은 항목이 마침 표본 많은 항목과 승률이 가까워졌을 때 티어 재정렬이 신뢰도 우선순위를 조용히 무너뜨릴 수 있었습니다.
  - `compFitPicks`("조합 기반 추천")·`combinedPicks`("둘 다 좋은 픽")는 대상에서 뺐습니다 — 전자는 애초에 실제 승률/게임 수 자체가 없는 태그 기반 추정치라 표본 신뢰도 개념이 적용될 데이터가 없고, 후자는 두 리스트(카운터/시너지)가 이미 각각 신뢰도 순으로 정렬된 뒤 교집합을 취하는 구조라 별도 처리가 없어도 대체로 신뢰도 높은 조합이 자연히 상위에 옵니다.

  순수 함수라 실제 스크래핑 데이터 없이도 Node로 직접 재구현해 단위 테스트했습니다: (1) 3게임 100% 승률이 500게임 55% 승률보다 아래로 가는 것, (2) 같은 구간 안에서는 게임 수와 무관하게 승률로만 정렬되는 것, (3) 100+/50~99/50 미만 세 구간의 순서가 어떤 극단적인 승률 차이에도 절대 안 바뀌는 것, (4) 표본 구간이 다르면 승률이 아무리 가까워도 챔피언 풀 티어 재정렬이 안 일어나는 것, (5) 같은 구간 안에서는 기존처럼 티어 재정렬이 정상 동작하는 것 — 5개 케이스 모두 통과를 확인했습니다.
- **"조합 비교" 탭 (포지션 없이 빠르게 팀 조합 비교)**: 실제 드래프트 타이머에 맞춰 픽을 일일이 입력하기 번거롭다는 요청에서 출발했는데, 논의 끝에 "포지션을 구분하지 않고 챔피언만 빠르게 비교 — 우리팀/상대팀 구분만 있고, 파워 커브·AP/AD 비율·챔피언 속성 등으로 조합적 우세를 비교"하는 새 탭으로 정리됐습니다. 기존 라인 카운터/픽 추천/빌드 세 탭은 건드리지 않고 완전히 독립된 4번째 탭으로 추가했습니다.
  - **입력**: 우리팀 5칸 + 상대팀 5칸, 포지션 라벨이 전혀 없는 단순한 보드입니다(`compCompareSlotsFor`, `src/app/page.tsx`). 챔피언을 고를 때마다 선택 창이 안 닫히고 빈 슬롯이 남아있는 한 바로 다음 슬롯으로 넘어가고(연속 입력), 검색창은 자동 포커스되며 Enter만 눌러도 첫 검색 결과가 바로 선택됩니다(`ChampionPicker`의 `quickInput` prop). 이 세 가지(연속 입력/자동 포커스/Enter 선택)는 **이 탭에만 적용**되고, 기존 라인 카운터/빌드/픽 추천 탭은 지금까지처럼 픽할 때마다 선택 창이 매번 닫힙니다 — 처음엔 픽 추천 탭 자체를 이렇게 바꿨다가, "그 기능은 다른 탭에 따로 추가해달라"는 요청으로 되돌리고 `mode === "compcompare"`일 때만 켜지도록 옵트인 처리했습니다.
  - **분석**: 새 로직은 전혀 없습니다 — `/api/compcompare`가 이미 픽 추천에서 쓰던 `analyzeTeamComp`(AP/AD 데미지 비중, 역할군 분포, 원거리 딜러/탱커/브루저 속성 세분화)와 `analyzeCompConcepts`(돌진/포킹/쌍포/한타/스플릿), 그리고 `getPowerCurve`(lol.ps 분당 승률)를 포지션 매개변수 없이 그대로 재사용해서 우리팀/상대팀 로스터 각각에 계산합니다. 화면에도 기존 `CompCard`/`CompConceptCard`/`ConceptMatchupNote` 컴포넌트를 그대로 재사용했고, 파워 커브만 포지션이 없어 라인 불일치 캐비어트(`laneNote`)가 필요 없는 `RosterPowerCurveCard`를 새로 만들었습니다.
  - **알려진 제약**: 실측 승률 조회가 전혀 없는 탭입니다 — 파워 커브만 실제 lol.ps 스크래핑 데이터고, 나머지(조합 분석/조합 컨셉)는 위 다른 탭들과 마찬가지로 Riot 공식 정적 데이터 기반 참고용 체크입니다(실제 5:5 조합 승률 데이터는 이 앱 어디에도 없음 — README 앞부분 참고).
  - **"내 맞 라이너" 카운터 픽 추천**: "상대 5명 중 내 맞 라이너일 확률이 가장 높은 3명을 뽑아서, 픽 추천과 같은 형식으로 카운터 픽을 보여달라"는 요청으로 추가했습니다. 원래 이 탭엔 포지션 개념이 없지만, 이 기능만은 예외라 포지션 탭(`.position-tabs`, 탑/정글/미드/원거리 딜러/서포터)이 조합 비교 탭에서도 함께 뜨도록 바꿨습니다 — 여기서 고르는 포지션은 "내가 이번에 픽할 포지션"이라는 뜻이라 안내 문구(`내가 픽할 포지션`)로 명확히 표시했습니다.
    - **"맞 라이너일 확률" 산정 방법**: lol.ps champSummary의 라인 점유율 필드(`top1LaneId`/`top1LaneRatio`)는 실제로 항상 0을 반환하는 것으로 이미 확인됐던 필드라(위 픽 추천/라인 카운터 섹션 및 코드 주석 참고) 이 값을 근거로 쓰지 않았습니다. 대신 이미 검증된 `getAggregatedLaneCounters(챔피언, 포지션)`를 상대 5명 각각에 대해 호출해서, 반환된 `entries[].primary.games`(그 포지션에서 그 챔피언을 상대로 실제 기록된 카운터 조회 표본 게임 수 총합)를 대리 지표로 씁니다 — 표본이 많다는 건 그만큼 그 챔피언이 그 라인에서 자주 등장한다는 뜻이라, 실측 라인 점유율이 없어도 상대적으로 신뢰할 수 있는 근사치입니다. 상대 5명을 이 총합 기준으로 정렬해 상위 3명만 추립니다(`computeLikelyEnemyLaners`, `src/app/api/compcompare/route.ts`).
    - **추천 형식**: 요청대로 픽 추천 탭과 동일한 UI를 재사용합니다 — `WinRateBar`/`TierBadge`/`PowerCurveBadge`/`CompFitBadge`/`KeyTagBadges`/`ConceptFitBadges`/`SourceBreakdown` 컴포넌트를 그대로 가져다 썼고, 서버 응답도 픽 추천의 `PickEntry`와 같은 모양(`championId`/`name`/`iconUrl`/`winRate`/`games`/`bySource`/`compFit`/`tier`/`keyTags`/`conceptFits` 등)입니다. 각 카운터 후보 챔피언의 점수는 실측 승률(`CANDIDATE_REAL_WEIGHT = 0.8`)과 상대 조합 적합도(`CANDIDATE_ENEMY_FIT_WEIGHT = 0.2`, `scoreEnemyCompFit`)를 블렌딩해 정렬합니다 — 픽 추천의 실제 승률:상대 조합 적합도 비중(약 4:1)을 그대로 따르되, 이 탭엔 아군 시너지 신호가 없어 두 값만으로 재정규화했습니다.
    - **의도적으로 제외한 것**: 아군 시너지 실측(`allySynergyMatchCount` 등), 후보의 파워 커브 대 상대 매치업(`powerCurveVsEnemyFit`), 라인전 골드/경험치차 실측(`laningStats`), 빌드(`build`)는 넣지 않았습니다 — 전부 "우리팀에서 정확히 어느 라인이 붙는지"가 확정돼야 계산할 수 있는 값들인데, 이 탭은 애초에 그 정보(우리팀 쪽 포지션 배치)를 아예 입력받지 않는 구조라 낼 수 없는 데이터입니다.
    - Playwright로 (1) 조합 비교 탭에서 포지션 탭과 안내 문구가 함께 뜨는 것, (2) 포지션을 고르면 `/api/compcompare` 요청에 그 포지션이 실려가는 것, (3) 상대 챔피언별 "OOO 상대 라인전 유리한 픽 (표본 N게임)" 제목과 카운터 픽 목록이 픽 추천과 같은 배지들(승률바/티어/파워커브/조합적합도 등)과 함께 뜨는 것, (4) 카운터 데이터가 빈 배열인 챔피언은 "카운터 데이터를 찾지 못했습니다" 안내가 뜨는 것, (5) 기존 라인 카운터/픽 추천/빌드 탭에는 포지션 탭이 여전히 정확히 한 번만 뜨는 것(회귀 없음)을 확인했습니다.

  버그 하나를 구현 중에 발견해 고쳤습니다: "다음 빈 슬롯이 있는지"를 React state 업데이터 함수(`setSlots((prev) => {...})`) 안에서 계산한 뒤 그 함수 바깥에서 곧바로 읽으려고 했는데, `setState`의 업데이터 함수가 그 이후 코드보다 먼저(동기적으로) 실행된다는 보장이 없어서 실제로는 매번 갱신 전 값을 읽는 바람에 "빈 슬롯이 남아있어도 매번 닫히는" 버그가 있었습니다. Playwright로 "연속 두 번째 픽에도 선택 창이 열려있는지"를 확인하는 과정에서 잡아서, 클로저의 현재 `slots` 값으로 미리 판단하도록 고쳤습니다. Playwright로 (1) 이 탭에서만 검색창 자동 포커스/연속 입력이 되는 것, (2) 라인 카운터/픽 추천 등 다른 탭은 예전처럼 한 번 고르면 선택 창이 바로 닫히는 것(회귀 없음), (3) 우리팀/상대팀 각각 채운 뒤 파워 커브·AP/AD 비중·조합 컨셉 결과가 실제로 뜨는 것(접힌 세부정보를 펼쳐서 확인)을 검증했습니다.
- **"아이템 빌드" 탭 (직접 만드는 6칸 아이템 빌드 + 가격·스탯·스탯별 검색)**: "아이템 정보를 공식적으로 수집할 수 있냐"는 질문에 "이미 이름/아이콘/태그는 Data Dragon `item.json`(공식, 스크래핑 아님)에서 가져오고 있고, 가격·스탯·설명도 같은 응답에 이미 들어있어서 확장만 하면 된다"고 답한 뒤, 이어진 요청으로 완전히 새로운 5번째 탭을 추가했습니다. 기존 4개 탭(챔피언 슬롯/포지션 탭/선택 바)과는 전혀 다른 성격(포지션도 팀도 없는 6칸 아이템 목록)이라, 그 슬롯 상태(`slots`/`activeSlotKey`/`pickerOpen`)를 전혀 재사용하지 않고 완전히 독립된 상태(`itemSlots`/`activeItemSlotIndex`/`itemPickerOpen`)로 구현했습니다 — 포지션 탭과 선택 바(`.selected-bar`, 스플래시 아트/조회 버튼)도 이 탭에서는 아예 숨깁니다.
  - **공식 데이터 확장**: `DDragonItem`(`src/lib/ddragon.ts`)에 이름/아이콘/태그 외에 `cost`(item.json의 `gold` 블록 — 기본가/총가/판매가), `stats`(`stats` 블록 — 공격력/주문력/체력/방어력 등 수치 보너스), `plainDescription`(`plaintext` 필드 — 항상 안전한 평문 요약), `availableOnSummonersRift`(`maps["11"]` — 소환사의 협곡에서 살 수 있는지)를 추가했습니다. `description` 필드(툴팁 렌더러 전용 커스텀 마크업, `<mainText>`/`<stats>` 등)는 일부러 안 씀 — `plaintext`만으로 충분하고, 임의 마크업을 파싱/렌더링할 이유가 없습니다. **알려진 제약**: item.json의 `stats` 블록은 "레거시" 수치 스탯만 담고 있고, 능력치 재사용 대기시간(어빌리티 헤이스트)·관통력·전능 흡혈·치유 및 보호막 강화 같은 최신 스탯은 여기 아예 없습니다(오직 설명 텍스트로만 존재) — 그런 스탯이 핵심인 아이템은 스탯 카테고리로 검색해도 안 잡힙니다.
  - **새 API**: `/api/items`(`src/app/api/items/route.ts`)가 `getItemsWithCache()` 전체에서 `purchasable && availableOnSummonersRift`인 것만 걸러 이름순으로 정렬해 클라이언트에 내려줍니다 — `/api/champions`가 이미 하던 것과 같은 패턴(서버가 판단해서 걸러진 목록만 클라이언트로).
  - **삭제된 아이템 / 하위(조합) 아이템 제외**: "삭제된 아이템은 없애고 하위 아이템도 없애달라"는 요청으로 필터를 두 개 더 추가했습니다.
    - **삭제된 아이템**: `purchasable` 하나로는 안 걸러지는 경우를 위해, item.json이 공식적으로 제공하는 `hideFromAll` 플래그(일반 아이템 목록/브라우저에 노출하면 안 되는 항목이라는 Riot 자체 표시 — 옛 매치 기록/툴팁이 계속 정상 조회되도록 데이터만 남겨둔 레거시 아이템 등)를 `DDragonItem.hideFromAll`로 새로 파싱해서, `!hideFromAll`인 것만 통과시킵니다.
    - **하위(조합) 아이템**: item.json의 `into` 배열(이 아이템이 무엇으로 업그레이드되는지)이 비어있지 않으면 "아직 완성되지 않은 조합용 재료"(예: 롱소드, 망토 등)로 보고 `DDragonItem.isComponentItem`으로 표시한 뒤 `!isComponentItem`인 것만 통과시킵니다 — 이 탭은 "완성된 빌드"를 만드는 용도라, 최종(완성) 아이템만 골라볼 수 있으면 되고 중간 재료 단계는 보여줄 필요가 없다는 판단입니다.
    - 두 필터 다 순수 함수 조건이라 실제 스크래핑 데이터 없이도 Node로 직접 재구현해서, 완성템(통과)/조합템(제외)/`hideFromAll` 아이템(제외)/구매 불가(제외)/맵 미지원(제외) 다섯 케이스가 전부 의도대로 걸러지는 것을 확인했습니다.
    - **실제 배포본에서 검증해본 뒤 이어진 문제 제기 — "중복된 아이템도 있고 대부분의 아이템이 빠져있고 삭제된 아이템도 많이 있어"**: 이 세션의 샌드박스는 Data Dragon으로 나가는 아웃바운드 네트워크가 전부 막혀 있어서(읽기 전용 `WebFetch`로도 확인 — `ddragon.leagueoflegends.com`이 egress 프록시에서 그대로 차단됨) 위 두 필터를 실제 최신 patch의 item.json 데이터로 검증할 방법이 없었습니다. 그래서 이번엔 실제 데이터 없이도 확신할 수 있는 것 하나를 더 고쳤습니다: `requiredChampion`(예: 칼리스타의 검은 창처럼 특정 챔피언 전용)/`requiredAlly`(오른 아군이 있어야 사는 강화 버전)가 설정된 변형을 `DDragonItem.isRestrictedVariant`로 새로 표시해서 제외했습니다 — 이런 변형은 대부분 일반 아이템과 **이름이 같아서** "중복된 아이템"으로 보이는 흔한 원인 중 하나이고, 어차피 아무 챔피언이나 살 수 있는 아이템도 아닙니다. 안전장치로 이름이 겹치는 항목이 남으면(위 세 플래그로 다 안 걸러지는 경우 대비) 첫 번째 것만 남기는 이름 기준 중복 제거도 추가했습니다. **다만 "대부분의 아이템이 빠져있다"는 제보는 이 필터들만으로 설명이 안 됩니다** — `hideFromAll`/`isComponentItem`가 실제 최신 데이터에서 예상보다 훨씬 많은 아이템에 걸려 있거나(정의를 잘못 짚었을 가능성), 다른 원인일 수 있는데 실제 응답을 보지 못해 확정할 수 없었습니다. 실제 `/api/items` 응답(또는 몇 개 예시 아이템 이름)을 받아야 정확히 고칠 수 있는 상태입니다.
    - **Data Dragon 플래그 기반 필터를 전설 아이템에 한해 이름 화이트리스트로 교체**: 위 요청 후 사용자가 "이 링크(namu.wiki의 '리그 오브 레전드/아이템/전설' 문서)가 가장 정확하다"며 그 문서의 목차(전사/원거리 딜러/암살자/마법사/탱커/서포터 계열별 전설 아이템 목록)를 모바일 스크린샷 두 장으로 직접 전달해줬습니다. `hideFromAll`/`isComponentItem`/`requiredChampion` 같은 Data Dragon 플래그만으로는 실제 상황과 안 맞는다는 게 실사용으로 이미 확인된 상태라, 전설(완성) 아이템은 이 플래그들 대신 **사용자가 지목한 그 문서에서 옮겨온 정확한 이름 목록**(`LEGENDARY_ITEM_NAMES`, 새 파일 `src/lib/legendaryItems.ts`, 120개)에 있는지로만 걸러지도록 `/api/items`를 바꿨습니다 — 전설이 아닌 아이템(신발)은 이 목록에 없는 별개 카테고리라 그대로 기존 플래그 기반 필터(`purchasable && availableOnSummonersRift && !hideFromAll && !isComponentItem && !isRestrictedVariant`)를 씁니다. 신발 외의 다른 카테고리(기본/조합 아이템, 소모품, 장신구, 정글 아이템 등)는 이 탭이 애초에 "완성된 6칸 빌드"를 만드는 용도라는 점에 맞춰 의도적으로 목록에서 뺐습니다(전설+신발만). **알려진 한계**: 이 이름 목록은 사람이 스크린샷의 작은 글씨를 눈으로 읽어서 옮긴 것이고, 이 세션은 namu.wiki에도(`WebFetch`로 직접 시도했으나 역시 egress 프록시에 차단됨) Data Dragon에도 접근할 수 없어 옮긴 이름을 실제 원본과 대조 확인하지 못했습니다 — 오탈자가 하나라도 있으면 그 아이템은 실제로 판매 중이어도 목록에서 빠집니다. 배포된 화면에서 안 보이는 전설 아이템이 있으면 정확한 이름을 알려주면 바로 추가할 수 있습니다.
    - **"저 탭에 있는 아이템은 필수로 포함되게 해줘"**: 처음 화이트리스트를 만들 때는 이름이 목록에 있어도 `purchasable`/`availableOnSummonersRift` Data Dragon 플래그를 여전히 같이 요구했는데, 바로 이어진 이 요청으로 그 두 조건을 뺐습니다 — 지금은 이름이 `LEGENDARY_ITEM_NAMES`에 있다는 것 하나만으로 무조건 포함됩니다. namu.wiki 목록에서 직접 확인된 진짜 현재 전설 아이템인데도 Data Dragon 쪽 플래그가 틀려서(애초에 이 문제 제기 자체가 그런 플래그 불일치 때문에 시작됨) 빠지는 걸 막기 위함입니다. 대신 같은 이름이 두 번 이상 나오는 경우(레거시 중복 id 등)를 대비해 이름 기준 중복 제거를 마지막 단계로 추가해서, "무조건 포함"이 다시 중복 문제를 일으키지 않게 했습니다.
  - **입력**: 6개 아이템 슬롯(신발 포함, 실제 인벤토리와 같은 칸 수 — 장신구는 가격/스탯이 의미 없어서 뺐습니다). 슬롯을 누르면 챔피언 픽커와 같은 전체 화면 오버레이가 뜨고, 이름 검색과 함께 **스탯 카테고리 칩**(공격력/주문력/치명타 확률/공격 속도/체력/마나/방어력/마법 저항력/이동속도/체력 재생/마나 재생/생명력 흡수, `ITEM_STAT_CATEGORIES`, `src/lib/itemStats.ts`)으로 "이 스탯을 주는 아이템만" 좁혀볼 수 있습니다(`ItemPicker`, `src/components/ItemPicker.tsx`) — 칩은 단일 선택(같은 칩을 다시 누르면 해제), 실제 상점 카테고리 탭과 같은 방식입니다. 같은 아이템을 여러 슬롯에 중복으로 넣는 것도 막지 않았습니다(소모품/스택형 아이템처럼 실제로도 여러 개 살 수 있는 경우가 있어서).
  - **합계·상세 정보**: 채워진 아이템들의 **총 가격**과, 겹치는 스탯 키는 그대로 합산한 **스탯 합계**(예: 방어구템 두 개가 둘 다 방어력을 주면 그 값을 더함 — 방어력/마법 저항력의 실제 피해 감소 공식 같은 게임 내 계산은 반영하지 않는 단순 합산이라는 점을 화면에도 명시)를 보여줍니다. 각 아이템 카드의 "상세 정보"(접이식)에는 `plainDescription`(공식 평문 설명), 전체 스탯 목록, 태그, 기본가/판매가가 모두 뜹니다.
  - Playwright로 (1) 이 탭에서 포지션 탭/선택 바가 숨는 것, (2) 슬롯을 누르면 아이템 픽커가 뜨는 것, (3) 스탯 카테고리 칩으로 필터링하면 해당 스탯을 가진 아이템만 남는 것, (4) 이름 검색이 함께 동작하는 것, (5) 아이템을 고르면 오버레이가 닫히고 슬롯이 채워지는 것, (6) 두 아이템을 채우면 총 가격과 스탯 합계(서로 다른 스탯은 각각, 겹치는 스탯은 아이템 값을 그대로 더한 값)가 정확히 뜨는 것, (7) 상세 정보를 펼치면 설명·스탯·기본가/판매가가 모두 뜨는 것, (8) "빈 슬롯으로 두기"가 정상 동작하는 것, (9) 다른 4개 탭은 포지션 탭/선택 바가 여전히 정상적으로 뜨는 것(회귀 없음), (10) 탭을 벗어났다 돌아오면 아이템 빌드가 초기화되는 것(다른 탭들과 같은 "탭 전환 시 초기화" 관례)을 확인했습니다.

## 새 사이트 추가하는 법

`src/lib/sources/registry.ts`의 `configs` 배열에 항목을 하나 추가하면 됩니다:

```ts
{
  id: "newsite",
  label: "새사이트",
  confidence: "low",
  slug: (s) => s.toLowerCase(), // 또는 toKebabSlug 등
  counterUrl: (slug, position) => `https://example.com/champions/${slug}/counters?position=${position}`,
  duoUrl: (adcSlug) => `https://example.com/champions/${adcSlug}/duos?position=adc`,
},
```

그 사이트가 Next.js/Nuxt 계열로 서버 렌더링되며 페이지에 통계 배열이 JSON으로 내장돼 있다면 이걸로 끝입니다. 완전히 다른 방식(별도 JSON API 등)을 쓰는 사이트라면 `src/lib/sources/types.ts`의 `StatSource` 인터페이스를 직접 구현하는 새 파일을 만들고 `registry.ts`의 `SOURCES` 배열에 추가하세요.

## 알려진 제한사항

- **소스별 페이지 구조 미검증** (위 "각 소스 연동 신뢰도" 표 참고) — 가장 먼저 확인이 필요한 부분입니다.
- 인메모리 캐시는 서버리스/재배포 환경에서 인스턴스마다 따로 놀고 쉽게 초기화됩니다. 완전히 신뢰할 캐시가 필요하면 Redis 등 외부 캐시로 바꾸는 걸 권장합니다.
- 어떤 사이트가 요청을 차단(403/429)해도 우회를 시도하지 않습니다. 라인 카운터/픽 추천처럼 여러 소스를 합치는 곳은 나머지가 살아있으면 그 소스만 빼고 계속 보여주고, 전부 막히면(또는 빌드 탭처럼 소스가 하나뿐인 경우) 화면이 그냥 비지 않고 "가져오지 못했습니다" 같은 짧은 안내를 보여줍니다 — 원인이 된 실제 HTTP 상태/에러 문구까지는 화면에 노출하지 않습니다(브라우저 개발자 도구 Network 탭에서 확인 가능). 반복적으로 막힌다면 조회 빈도를 줄이거나 해당 사이트에 이용 허가를 문의하는 걸 권장합니다.
- 5개 챔피언 전체 조합 평가처럼 이 사이트들의 카운터/듀오/빌드 페이지에 없는 통계는 제공하지 않습니다 (실제 존재하는 데이터만 보여주는 쪽으로 방향을 잡았습니다).
- 빌드 추천은 lol.ps 한 곳의 값만 보여줍니다(다른 5개 소스와 평균/합산하지 않음) — 화면에도 "lol.ps 기준"이라고 명시해뒀습니다. 카운터/듀오처럼 여러 소스를 비교해서 보여주는 형태가 아닙니다.
- 바텀 듀오 시너지는 op.gg 등에서만 지원되고 lol.ps는 아직 미지원입니다 — lol.ps에 `duo-list.json`이라는 별도 API가 있는 걸 URL로는 확인했지만 응답 본문(Brotli 압축)을 아직 못 받아서 필드 구조를 모릅니다.
- 내 챔피언 풀은 브라우저 `localStorage`에만 저장됩니다 — 계정/서버 개념이 없어서 다른 기기나 브라우저에서는 다시 등록해야 합니다. 포지션별로 따로 관리되며(위 "챔피언 풀을 포지션별로 분리" 참고), 픽 추천의 "내 픽 추천"(카운터/시너지/둘 다 좋은 픽) 세 목록에만 적용되고, 실측 데이터 기반 전체 시너지·챔피언 특성 기반 조합 분석·라인 카운터/빌드 탭에는 적용되지 않습니다(그 기능들은 "무엇을 픽할지 추천"이 아니라 이미 정해진 챔피언을 분석/조회하는 기능이라 풀 필터링 대상이 아닙니다).
- 모바일 UI를 위해 페이지 전체에서 텍스트 선택을 꺼뒀습니다(검색창 등 입력 필드는 예외). 그래서 위 "로컬에서 실행해보고 안 되면" 항목에서 안내하는 것처럼 에러 메시지를 드래그로 복사하기는 어렵습니다 — 브라우저 개발자 도구(Console/Network 탭)에서 복사하거나 스크린샷으로 공유해주세요.
